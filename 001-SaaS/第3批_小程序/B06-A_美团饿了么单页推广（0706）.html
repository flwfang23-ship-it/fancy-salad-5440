B06-A 美团饿了么单页推广

本功能在现有权益页之外，新增美团单页和饿了么单页两个固定推广页面。客户不需要拖拽组件，只需要分别为每个单页配置上方活动和下方活动。推广位管理处为每个推广位新增美团单页链接和饿了么单页链接，推广链接同时携带推广位 ID 和页面 ID：推广位 ID 决定收入归属和取链参数，页面 ID 决定用户打开权益页、美团单页还是饿了么单页。

1. 需求背景与目标

1.1 为什么要做

现有权益页由客户自行组装组件，适合承载多个平台和多个活动的综合权益展示。但在推广精准粉场景中，客户经常只需要把用户直接引导到一个平台主题明确的首页单页，例如美团推广单页或饿了么推广单页。继续让客户通过权益页组件搭建，会增加配置成本，也不利于形成统一的推广落地页样式。

本功能通过平台预置两个固定单页，降低客户配置门槛。客户只需要为美团单页和饿了么单页分别选择上方活动和下方活动，系统即可在推广位管理处生成对应页面的推广链接。C 端用户打开链接后进入指定单页，并在页面内选择其中一个活动继续参与。

改造前

客户推广入口主要指向权益页
        -> 权益页由客户自行拖拽组件搭建
        -> 想推广美团或饿了么精准粉时，客户仍需要理解组件配置和页面布局

改造后

权益页继续保留
        +
平台新增美团单页和饿了么单页
        +
客户分别配置每个单页的上方活动和下方活动
        -> 推广位管理处生成 3 类页面链接
        -> C 端用户按页面 ID 进入对应页面

1.2 一句话业务模型

推广位 ID
        +
页面 ID（0=权益页，3=美团，5=饿了么）
        +
客户为美团/饿了么单页配置的上方活动和下方活动
        -> 生成可投放的页面推广链接
        -> 用户打开指定页面并点击活动
        -> 收入仍按推广位 ID 完成归因

1.3 最终目标

  • 三类页面可投放： 客户可在同一推广位下投放权益页、美团单页和饿了么单页。
  • 页面选择不改变归因： 页面 ID 只决定打开哪个页面，收入归属仍由推广位 ID 决定。

3. 第一阶段：单页与活动准备

表格类型：-

链接生成不要求客户手工拼接： 客户只复制系统生成的链接，不手动填写页面 ID 或推广位 ID。

6.1 C 端页面访问与展示 - 移动端展示页（新增页面）

业务背景

对下游影响：用户点击活动后进入对应活动承接页；产生收入时，系统沿用推广位归因规则。
页面类型：移动端展示页

C 端用户打开推广链接后，系统解析链接中的页面 ID 和推广位 ID。页面 ID 决定当前展示权益页、美团单页还是饿了么单页；推广位 ID 写入当前访问的归因上下文。用户在美团或饿了么单页中看到上方活动和下方活动两个入口，点击其中一个入口后继续参与活动。

页面交互

交互：打开推广链接
业务用途： 用户进入客户投放的指定页面。
点击结果： 系统解析推广位 ID 和页面 ID，渲染对应页面。

交互：点击上方活动
业务用途： 用户选择当前单页的第一个活动入口。
点击结果： 进入活动对应承接页或执行活动对应参与方式。

交互：点击下方活动
业务用途： 用户选择当前单页的第二个活动入口。
点击结果： 进入活动对应承接页或执行活动对应参与方式。

业务逻辑

页面选择与归因分离： 页面 ID 只决定当前渲染哪个页面，不参与收入归因优先级判断。推广位 ID 才是收入归属的核心依据。

单页内活动沿用当前推广位： 用户在美团单页或饿了么单页点击任一活动时，活动后续取链和归因上下文沿用当前推广链接中的推广位 ID。

归因规则沿用既有能力： 小程序端继续使用用户标签归因，H5 端继续使用页面参数绑定归因。新增页面不改变归因窗口期、默认推广位兜底和推广位删除后的历史记录规则。

8. AI 维护说明

本章用于 AI 阅读和维护，不向业务读者重复解释正文。修改本文时，应先保护“页面 ID 决定落地页、推广位 ID 决定归因”的核心关系，再检查单页配置、推广位链接和 C 端访问三处是否同步。

8.1 文档设计理念

本文采用“人类阅读正文 + AI 维护说明”的双层结构。

人类正文的目标是让读者看清：客户为什么需要两个固定单页，客户在哪里配置上下活动，推广位管理处为什么新增两条链接，C 端如何根据页面 ID 打开对应页面，以及收入为什么仍然归到推广位。

AI 维护说明集中记录边界、术语、上下游检查和待确认逻辑，不把接口参数、数据表结构、短链算法和未确认异常文案写入正文。

8.2 正文组织原则

  • 正文按业务发生顺序组织：单页与活动准备 -> 客户配置单页活动 -> 推广位管理新增链接 -> C 端访问与归因。
  • 不把美团单页和饿了么单页拆成两篇文档。两者结构相同，只是页面 ID 和活动平台范围不同。
  • 不把新增单页误写为权益页组件。权益页继续走拖拽搭建，美团和饿了么单页走固定双活动配置。
  • 不把本功能写成独立“多活动 H5 链接管理”。本功能借用“双活动”的上下版位概念，但链接入口在推广位管理处。
  • 页面 ID 和推广位 ID 必须在正文中始终分开说明：页面 ID 选页面，推广位 ID 做归因。

8.3 泳道和参与方识别规则

本文涉及三个业务参与方：

  • SaaS 总后台：准备可推广活动和固定单页能力。
  • 客户端后台：客户配置单页上下活动，并在推广位管理处复制链接。
  • C 端用户：打开链接、查看页面、点击活动。

保存配置、生成链接、解析页面 ID、绑定推广位 ID 和执行归因属于系统自动处理结果，只写入对应页面或业务逻辑，不作为独立业务参与方写入泳道。不得把内部接口、定时任务、缓存、路由服务或短链服务作为业务参与方写入泳道。

8.4 上下游与模块边界检查

推广位链接展示方式 推广位列表、推广位编辑抽屉、取链复制入口

模块边界：

  • 权益页功能负责客户拖拽组件搭建权益页，不负责美团/饿了么固定单页的上下活动配置。
  • 本功能负责美团/饿了么固定单页配置、推广位页面链接扩展和 C 端页面选择。
  • 推广位管理负责推广位本身的创建、分组、删除和基础展示。
  • 收入归因规则负责推广位 ID 的归因执行，不因页面 ID 扩展而改变优先级。

8.5 术语、字段和状态同步规则

  • 全文统一使用“权益页”“美团单页”“饿了么单页”“页面 ID”“推广位 ID”“上方活动”“下方活动”。
  • 页面 ID 固定口径：0=权益页，3=美团单页，5=饿了么单页。
  • “美团单页链接”和“饿了么单页链接”是推广位页面链接，不是独立多活动 H5 链接。
  • “上方活动”和“下方活动”是固定版位，不是客户可新增的组件。
  • “已配置/未配置”描述单页配置完整性，不描述推广位状态。
  • “推广位删除”继续沿用推广位管理和归因规则中的软删除、历史链接继续有效、默认推广位兜底等既有口径。

8.6 不得混淆

  • 页面 ID 不等于推广位 ID。页面 ID 决定打开哪个页面，推广位 ID 决定收入归属。
  • 美团单页/饿了么单页不等于权益页组件。客户不拖拽这两个页面的组件。
  • 美团单页/饿了么单页不等于多活动 H5 链接记录。本功能不要求客户新建一条独立多活动链接。
  • 上方活动/下方活动不等于两个推广位。两个活动入口沿用当前推广链接中的同一个推广位 ID。
  • 复制链接不等于单页配置完成。链接可以生成，但单页是否完整展示取决于该页面上下活动配置。
  • 后台配置修改不等于历史链接地址变化。已复制链接地址携带的推广位 ID 和页面 ID 不变，页面展示读取最新配置。

8.7 待确认逻辑

  1. 美团单页或饿了么单页未完整配置上下活动时，推广位管理处是否允许复制对应页面链接？
  2. 单页未完整配置时，C 端是展示缺失提示页，还是展示已配置的单个活动入口？
  3. 同一个单页的上方活动和下方活动是否允许选择同一个活动？
  4. 活动下架、失效或推广能力缺失后，C 端对应版位展示什么文案，是否保留最后一次有效内容？
  5. 页面 ID 缺失、格式错误或无法识别时，是默认进入权益页，还是展示异常页？
  6. 美团单页和饿了么单页是否需要独立预览入口？如果需要，预览是否携带默认推广位 ID？
  7. 推广位管理处三类链接是在列表直接展示，还是收敛到“取链”弹窗或抽屉中展示？
  8. 美团单页和饿了么单页是否需要配置页面标题、背景图、按钮文案等视觉内容，还是完全由固定模板决定？
  9. 单页配置变更是否需要记录操作日志或历史版本？
  10. C 端点击上下活动后的具体承接方式，是否完全沿用活动自身推广能力，还是需要针对美团/饿了么单页做特殊处理？

需求背景与目标

1.1 为什么要做

每月 1 号、15 号有口令自动更新任务，权益页联盟组件按节点拉取跳转链接，企微侧有推送任务持续运行，用户访问侧 H5 和小程序都可能出现封禁或异常，收入归因侧有兜底逻辑报警。这些环节任何一处异常都可能直接影响收入，但目前缺少统一的巡检指引，运营人员排查时容易遗漏环节，错过最佳处理窗口。

本指引把整条链路按 运营取链 → 企微推送 → 用户访问 → 收入归因 4 个阶段串成一条主线，明确每个阶段的检查节点、通知规则和处理方式。

口令自动更新

①当前环节：① 运营取链 - 口令自动更新
对下游影响口令是下游企微推送、用户访问所依赖的链接凭证，口令一旦过期未更新，会导致下游链接失效、用户无法访问、收入跑偏。

业务背景说明

  • 口令有效期 30 天：每个口令自生成起 30 天过期，需在过期前完成更新。
  • 更新节奏：每月 1 号、15 号定时触发批量更新任务，覆盖所有有效期即将到期的口令。
  • 更新维度：以"活动 → 推广位"维度进行更新；同一活动下可能有多个推广位，逐个更新。
  • 通知维度：以"活动"维度进行通知，将同一活动下所有推广位的更新结果聚合后发送一条通知。

通知规则

检查结果 通知文案 是否通知
正常 口令批量更新任务已完成，本次无异常 是（发送正常通知）
异常 xxxxxx、xxxxxx 活动口令更新存在异常，请及时登录查看 是（按活动维度列出异常活动名称）

通知内容字段说明

  • 活动名称：异常通知中按活动维度列出，每条异常活动的所有失败推广位聚合到该活动名下。
  • 结果状态：正常 / 异常。
  • 通知去向：飞书"自动化通知测试"群。

注意事项与坑点

  • 按活动维度聚合：通知时不要按推广位维度逐条发送，否则群消息过多；同一活动下多个推广位异常，合并为一条通知。
  • 正常也通知：本节点正常情况会发送"本次无异常"通知，便于运营人员确认任务执行；与 3.2 权益页检索（正常不通知）规则不同，需区分记忆。
  • 异常通知要带活动名：异常通知中必须列出异常活动的名称，便于运营人员直接定位。
  • 1 号、15 号节点前关注群消息：建议运营人员在 1 号、15 号任务执行时点后留意"自动化通知测试"群，发现异常立即登录处理。

业务逻辑

口令更新是下游链路的前置保障：本节点是 4 阶段链路的起点。口令更新成功后，下游企微推送、用户访问所依赖的链接才能保持有效；口令更新失败的活动，下游推送和访问都会受影响，需在本节点异常通知后第一时间处理，避免影响扩散。

权益页检索

①当前环节：① 运营取链 - 权益页检索
对下游影响联盟组件通过接口拉取跳转链接，一旦未执行拉取，链接缺失，收入会跑到"兜底收入"，这是业务不想看到的异常结果。本节点的目标是保障所有联盟活动都有链接，避免收入跑偏到兜底。

业务背景说明

  • 联盟组件机制：小程序权益页内的联盟组件通过接口拉取跳转链接，跳转链接是用户进入活动、产生订单、归因收入的凭证。
  • 兜底收入问题：若链接未拉取成功，用户访问后产生的收入会跑到"兜底收入"，无法归因到正确活动，业务侧无法统计和对账。
  • 检索触发节点：
  • 节点 ①：客户创建新推广位——新增推广位后需保障其对应的联盟组件链接被拉取。
  • 节点 ②：后台更换了组件关联的活动——活动变更后需保障所有组件在新活动下都有链接。
  • 保障目标：保障所有的组件、联盟活动都有链接。

检索触发节点说明

触发节点 触发动作 检查范围
① 客户创建新推广位 新推广位对应的联盟组件是否有链接
② 后台更换了组件关联的活动 更换后所有组件、所有联盟活动是否都有链接

通知规则

检查结果 通知文案 是否通知
正常 — 否（不通知）
异常 【ID=01】的【言成科技】客户的权益页组件【美团叠加红包】异常，请及时处理 是（发送异常通知）

通知内容字段说明

  • 客户 ID：异常通知中以 【ID=XX】 格式带出客户 ID。
  • 客户名称：从客户的"备注字段"读取（如"言成科技"）；不读客户主体名称，只读备注。
  • 组件名称：异常的联盟组件名称（如"美团叠加红包"）。
  • 异常原因：链接未拉取 / 链接失效。
  • 通知去向：飞书"自动化通知测试"群。

注意事项与坑点

  • 正常不通知：本节点正常情况不发送通知，避免群消息冗余；只有异常时才通知。这与 3.1 口令更新（正常也通知）规则不同，需区分记忆。
  • 客户名称读备注字段：通知中的客户名称（如"言成科技"）必须来自客户的备注字段，不读主体名称——主体名称可能与业务侧称呼不一致。
  • 保障所有组件：节点 ② 更换活动后必须检查所有组件在新活动下是否都有链接，不能只检查被更换的组件。
  • 异常通知要带 ID + 备注名 + 组件名：异常通知必须按 【ID=XX】的【备注名】客户的权益页组件【组件名】异常 格式发送，便于运营人员直接定位客户和组件。
  • 兜底收入是结果不是源头：兜底收入是链接缺失后的结果表现，本节点要前置保障链接有效，避免走到兜底。

业务逻辑

权益页检索是收入归因的前置保障：联盟组件的跳转链接是收入归因到活动的凭证，链接缺失会导致收入跑到"兜底收入"无法归因。本节点通过在"客户创建新推广位"和"后台更换组件关联活动"两个触发点进行检索，前置发现链接缺失，避免下游收入归因异常。本节点正常不通知，与 3.1 口令更新通知规则不同，运营人员需留意区分。

企微号异常

②当前环节：② 企微推送 - 企微号异常
对下游影响企微号异常会导致群发任务无法执行，下游 4.2 推送结果中"实际群发企微号数"将低于"预计"，进而影响用户访问量。

推送结果通知

②当前环节：② 企微推送 - 推送结果通知
对下游影响推送结果反映企微号群发任务的执行情况；实际群发企微号数低于预计数时，意味着部分用户未收到推送，会直接影响下游用户访问量。

业务背景说明

  • 系统接入企微推送：本系统已接入企微推送功能，能获取每天的群发结果数据。
  • 定时推送节点：每天下午 14:00 自动汇总当天群发结果并推送到飞书"自动化通知测试"群。
  • 通知维度：按客户维度逐个列出，每个客户一条数据块。
  • 客户名称读取：来自客户的"备注字段"，不读主体名称（与 3.2 权益页检索规则一致）。

通知规则

检查结果 通知文案 是否通知
每日定时 按客户维度逐条列出当天群发数据 是（每天 14:00 定时通知，无论正常异常都推送）

通知内容字段说明（按客户维度逐条列出）

每个客户一条数据块，包含以下字段：

  • 客户 ID：以 【ID=XX】 格式带出客户 ID。
  • 客户名称：从客户的"备注字段"读取（如"言成科技"、"无人科技"、"彬哥"）；不读主体名称。
  • 当天群发用户数：当天预计要群发的用户总数。
  • 预计群发企微号数：当天计划使用的企微号数量。
  • 实际群发企微号数：当天实际成功群发的企微号数量。
  • 成功率：= 实际群发企微号数 / 预计群发企微号数（百分比）。
  • 注（异常提示）：当实际 < 预计时显示，格式"有 XXX 个号未正常群发，请登录检查"。

字段计算说明

  • 未正常群发数 = 预计群发企微号数 - 实际群发企微号数（示例：1441 - 1220 = 221）。
  • 成功率 = 实际群发企微号数 / 预计群发企微号数 × 100%（示例：1220 / 1441 ≈ 85%）。
  • "注"的显示条件：当未正常群发数 > 0 时显示"有 XXX 个号未正常群发，请登录检查"；当未正常群发数 = 0（实际 = 预计）时不显示注。

注意事项与坑点

  • 每天定时通知：本节点是每日定时通知（每天 14:00），无论正常异常都推送，与 3.1 口令更新（定时 + 正常也通知）规则类似；与 3.2 权益页检索（正常不通知）规则不同。
  • 按客户维度列出：通知时按客户维度逐条列出，每个客户一条数据块；不要把多个客户的数据混在一起。
  • 客户名称读备注：客户名称必须来自备注字段，与 3.2 权益页检索规则一致，不读主体名称。
  • "注"的显示条件：未正常群发数 > 0 时显示，= 0 时不显示；不要无脑每条都带"注"。
  • 实际 < 预计即异常：实际群发企微号数低于预计数即视为异常，运营人员收到"注"提示后需登录检查。
  • 下午 14 点后留意群消息：建议运营人员每天 14:00 后留意"自动化通知测试"群，发现异常立即登录处理。

业务逻辑

推送结果是用户访问的前置指标：企微推送是用户访问的引流入口，实际群发企微号数直接决定下游用户访问量。本节点每天 14:00 定时通知按客户维度列出的群发结果，运营人员可基于"实际 < 预计"判断哪些客户有异常，及时登录检查企微号状态，避免下游用户访问量异常下降。本节点是定时通知，与 3.2 权益页检索（事件触发 + 正常不通知）规则不同，但与 3.1 口令自动更新（定时 + 正常也通知）规则类似。

H5 是否被封

③当前环节：③ 用户访问 - H5 是否被封
对下游影响H5 被封后用户无法访问对应链接，下游用户访问量异常下降，影响收入归因。

业务背景说明

  • 维护一级域名清单：系统后台维护一份一级域名清单，清单内的每个域名都纳入访问量监控。
  • 定时记录访问量：定时任务每 5 分钟执行一次，记录清单内每个一级域名的访问量。
  • 今日 vs 昨日同时段对比：每次巡检取"今日 0 点至当前时刻的累计访问量"与"昨日 0 点至昨日同一时刻的累计访问量"对比；必须按同时段口径对比，否则凌晨时段今日累计天然远小于昨日全天，会大面积误报。
  • 用访问量暴跌反推 H5 被封：H5 域名一旦被封或被拦截，最直接的表现就是访问量突然暴跌；本节点通过监控一级域名访问量跌幅，第一时间发现 H5 可访问性异常。

报警规则

检查结果 通知文案 是否通知
正常（访问量上涨，或跌幅 ≤ 20%） — 否（不通知）
异常（跌幅 > 20%） 域名：xxxxxxxxxx
时间：2026/9/23 14:48
今日-访问量：3232
昨日-访问量：4310
差值25%大于20%，请及时登录后台排查问题		 是（发送业务报警，按一级域名维度逐条列出）

报警内容字段说明

  • 域名：触发报警的一级域名（来自域名清单）。
  • 时间：本次巡检触发报警的时间，格式 yyyy/M/d HH:mm（如 2026/9/23 14:48）。
  • 今日-访问量：今日 0 点至当前时刻，该一级域名的累计访问量。
  • 昨日-访问量：昨日 0 点至昨日同一时刻，该一级域名的累计访问量（同时段口径）。
  • 差值：跌幅百分比 = （今日-访问量 - 昨日-访问量）/ 昨日-访问量 × 100%；报警时按跌幅绝对值展示（如 -25% 展示为"差值25%"）。
  • 通知去向：飞书"自动化通知测试"群。

差值25%大于20%，请及时登录后台排查问题

域名：AAAAAAAA

今日-访问量：3232
昨日-访问量：4310
差值25%大于20%，请及时登录后台排查问题

阈值计算说明

  • 跌幅公式：跌幅 = （今日-访问量 - 昨日-访问量）/ 昨日-访问量 × 100%。
  • 触发条件：跌幅 < -20%（即今日访问量比昨日同时段掉了两成以上）时触发业务报警；跌幅在 20% 以内以及访问量上涨均不报警。
  • 示例计算：昨日同时段访问量 4310，今日访问量 3232，跌幅 =（3232 - 4310）/ 4310 × 100% ≈ -25%，跌幅绝对值 25% > 20%，触发报警。
  • 同时段对比：每 5 分钟巡检时，对比的必须是"今日截至当前时刻"与"昨日同一时刻"的累计值，不能直接对比昨日全天数据。

注意事项与坑点

  • 只报暴跌：本节点仅在访问量跌幅超过 20% 时报警，访问量上涨不报警；目的是发现 H5 被封/被拦截等可访问性故障，而非监控日常流量波动。
  • 必须同时段对比：今日累计访问量要与昨日同一时刻的累计访问量对比，严禁直接对比昨日全天数据，否则每天凌晨都会误报。
  • 按一级域名维度逐条列出：同一巡检周期内多个域名触发报警时，每个域名一条数据块，不要把多个域名合并成一条。
  • 每 5 分钟巡检一次：域名访问量每 5 分钟记录并判断一次，报警延迟最多 5 分钟；收到报警后请及时登录后台排查域名状态。
  • 正常不通知：本节点正常情况不发送通知，与 3.2 权益页检索、5.2 小程序异常规则一致；与 3.1 口令更新、4.2 推送结果（定时通知）规则不同。

业务逻辑

访问量暴跌是 H5 被封最直接的信号：H5 链接依赖一级域名对外提供访问，域名一旦被封或被拦截，用户侧立即表现为访问量断崖式下降。本节点每 5 分钟对域名清单内所有一级域名做"今日 vs 昨日同时段"访问量对比，跌幅超过 20% 即按域名维度推送业务报警，帮助运营人员在用户大规模反馈前发现 H5 可访问性问题，避免下游用户访问和收入归因持续受损。本节点正常不通知，与 3.2、5.2 规则一致。

小程序异常

③当前环节：③ 用户访问 - 小程序异常
对下游影响小程序收到违规通知后可能进入风控流程，若不及时处理可能导致小程序被限制访问或下架，下游用户访问和收入归因均会中断。

业务背景说明

  • 入驻小程序数量多：本系统后台会入驻很多小程序，每个小程序都可能在微信侧收到违规通知。
  • 目前仅通知"违规通知"：本节点目前仅监听接口拉取到的"违规通知"这一类异常，其他类型的异常暂不通知。
  • 定时检索节点：每天 17:00 自动检索当天是否有小程序收到违规通知。
  • 客户名称读取：来自客户的"备注字段"；若无备注则显示为"-"（与 3.2、4.2 客户名称规则一致——都读备注，但本节点多了"无则显示-"的兜底）。

  • 客户 ID：以 【ID=XX】 格式带出客户 ID。
  • 客户名称：从客户的"备注字段"读取（如"言成科技"）；无备注时显示为"-"（这是本节点独有的兜底规则）。
  • 小程序名称：违规的小程序名称（如"外卖干饭小掌柜"）。
  • APPID：违规的小程序 AppID（如"xxxxxxxxxx"）。
  • 违规通知内容：来自接口拉取的"违规通知"，按原文带出。
  • 违规时间：违规通知的时间戳，从接口返回字段读取（如"2026-09-21 14:30:00"），与 APPID 共同组成违规记录的唯一标识。
  • 是否已通知：以 APPID + 违规时间 作为唯一标识判断；若本条违规通知已发送过群消息，则不再重复通知；若未通知过则发送。

是否已通知去重机制

  • 唯一标识：以 APPID + 违规时间 作为每条违规通知的唯一键。
  • 去重判断：每天 17:00 检索时，对每条拉取到的违规通知先查"是否已通知过"：
  • 已通知过 → 跳过，不重复发送。
  • 未通知过 → 发送群消息，并标记为"已通知"。
  • 存储位置：是否已通知状态持久化在系统后台（按 APPID + 违规时间维度记录），跨天去重，避免同一条违规通知在多个检索周期内被重复推送。
  • 新违规才通知：只有当小程序首次收到一条新的违规通知（APPID + 违规时间在已通知记录中不存在）时才发送群消息；同一小程序若已通知过该违规时间点的违规，下一次检索到同一条不再重复通知。

注意事项与坑点

  • 仅通知违规通知：本节点目前仅通知接口拉取到的"违规通知"这一类异常，其他类型的小程序异常暂不通知；后续若需扩展通知范围，再单独补充节点。
  • 正常不通知：本节点正常情况不发送通知，避免群消息冗余；与 3.2 权益页检索规则一致；与 3.1 口令更新、4.2 推送结果（定时通知）规则不同。
  • 客户名称无备注显示"-"：客户名称读备注字段，若无备注必须显示为"-"作为兜底，不要显示客户主体名称，也不要显示空白。
  • 按小程序维度逐条列出：每个违规的小程序一条通知，不要把多个小程序的违规通知合并。
  • 按 APPID + 违规时间去重：每条违规通知的唯一标识由 APPID + 违规时间组成，已通知过的不重复发送；这是"是否已通知"字段的核心判断逻辑，避免同一条违规通知被多次推送到群里。
  • 17 点后留意群消息：建议运营人员每天 17:00 后留意"自动化通知测试"群，发现违规通知立即登录小程序后台处理。
  • 违规通知要及时处理：违规通知若不及时处理，可能导致小程序被限制访问或下架，下游用户访问和收入归因都会中断。

业务逻辑

小程序异常是用户访问的最后一道关：小程序是用户访问链路的核心载体，一旦小程序因违规通知被限制访问或下架，下游用户访问和收入归因都会中断。本节点每天 17:00 定时检索违规通知，发现异常及时上报，与 5.1 H5 是否被封共同构成用户访问侧的检查闭环。本节点正常不通知，与 3.2 权益页检索规则一致；与 3.1 口令更新、4.2 推送结果（定时通知）规则不同。

收入逻辑报警

④当前环节：④ 收入归因 - 收入逻辑报警
对下游影响收入逻辑报警反映归因链路异常（如收入跑兜底、归因缺失等），不及时处理会导致业务侧无法统计和对账。

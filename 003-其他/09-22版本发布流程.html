需求背景与目标

1.1 为什么要做

  • 文档类型：版本发布流程指引手册——把整条发布闭环拆成 10 个整数步骤的标准操作流程。
  • 适用场景：每次版本发布前后，从需求确认到上线通知的全流程操作与对齐。
  • 解决问题：发布信息只在少数人手里、测试用例临场补、运营/UI 验收滞后、发版通知遗漏，导致方向性返工与上线后才知道。
  • 核心目标：让需求透明化，所有人都知道发布了什么，并保障发布质量；每个节点都有单一负责人。
  • 主要角色：产品（含UI）、开发人员（含东武）、运营（含利珠），其他角色为被通知方。

当前版本发布的痛点：每次发布前只有少数人知道要发什么、什么时候发、谁负责验收；测试人员接到任务时常常不知道测试用例在哪里；运营和UI在发布前才发现交互方向不对，临时返工；上线后通知遗漏，导致有人第二天才知道版本已经更新。本指引把整条发布闭环拆成 10 个整数步骤，每个步骤都有明确负责人，让所有人都能在任何时点查到"现在在等谁、下一步该谁动、卡在哪个环节"，并保障发布质量不依赖个人记忆。

1.3 最终目标

  • 过程透明化：任何角色在任何时点都能查到当前环节、负责人、上下游依赖，避免"不知道卡在谁"。
  • 质量前置：交互方向在开发动手前由运营验收；测试用例由开发自测后产出，再交测试人员，避免临场补漏。
  • 发布可追责：每个节点都有单一负责人；提交前 6 小时发通知；产品做最终验收关卡；上线后通知全员。

业务流程

2.1 多方业务泳道图

泳道图需要同时表达状态时，采用以下原则：

  • 编号节点只写参与方实际执行的业务动作。
  • 状态标注写在触发该状态的动作之后，不占用新的流程序号。
  • 一张泳道图只展示核心状态主线。本指引核心业务对象为版本发布记录（状态：版本范围已确认 → 产品方案已产出 → 交互验收已通过 → UI已交付 → 测试用例已产出 → 提交前6小时通知已发出 → 测试已通过 → 终验已通过 → 已上线 → 已通知全员）。
  • 不得使用动作名称代替中间状态。

2.2 阶段划分与阅读说明

后续正文按照业务实际发生顺序线性展开，不按角色分别集中介绍。根据当前发布闭环，可划分为：

1. 第一阶段：需求与方案（主要参与方：产品）：产品与东武（属开发侧，本步骤共同确认）共同确认版本范围与发布时间并将结论同步利珠（属运营侧，本步骤接收同步）；产品分解需求产出产品方案与交互方案；运营在开发动手前先验收交互，不通过则回到产品调整方案。

2. 第二阶段：开发与测试准备（主要参与方：开发人员）：开发人员与UI（属产品侧，本步骤同步绘图）并行启动；开发人员写测试用例并完成自测；提交版本前6小时由产品发出发版通知。

3. 第三阶段：测试与返工（主要参与方：运营）：利珠（属运营侧，本步骤组织测试）拿到测试用例后组织人员测试；测试不通过则开发人员返工修改，由利珠复测，循环直到测试通过。

4. 第四阶段：发布上线（主要参与方：产品）：产品进行最终验收，验收通过后由产品/开发人员完成上线，并通知所有人（含"其他"角色）。

2.3 页面类型说明

本指引为版本发布流程操作指引文档，所有阶段小节统一使用「内容页」类型——纯文本指引，无字段表、无页面骨架、无列表交互弹窗。正文承载操作步骤、注意事项、关键产出物和负责人。

确认版本需求

①当前环节：① 确认版本需求及发布时间
页面路径线下沟通 / 项目周会
对下游影响本步骤产出的版本范围与发布时间将作为后续所有步骤的节奏锚点；产品据此分解需求，开发据此排期，利珠据此安排测试人员，发版通知据此发出。

负责人与参与方

  • 负责人：产品
  • 共同决策：东武
  • 被同步方：利珠

操作步骤

1. 产品与东武共同确认本次发布的版本范围（含哪些需求项、不含哪些）。

2. 双方共同确认发布时间（精确到日期，必要时精确到小时）。

3. 产品将最终信息（版本范围 + 发布时间 + 关联需求清单）同步给利珠。

4. 利珠收到后回复确认，记入测试排期。

关键产出物

  • 版本范围清单：本次发布包含的需求项列表。
  • 发布时间：精确到日期/小时。
  • 同步记录：产品同步给利珠的凭证（聊天截图/邮件/周会纪要）。

注意事项与坑点

  • 版本范围必须双方书面确认：口头沟通无效，必须有可追溯的同步记录。
  • 发布时间一旦确认，不轻易变更：变更需走重新同步流程，并通知所有已排期人员。
  • 同步利珠不能晚于步骤 6 发版通知：利珠需要时间安排测试人员，至少留出 6 小时通知窗口。

业务逻辑

产品+东武共同决策：产品提出建议范围，东武确认；任一方有异议必须当场解决，不进入下一步。本步骤产出的版本范围将逐字进入步骤 6 的发版通知内容，避免发版时口径与最初确认不一致。

分解需求

②当前环节：② 分解需求
页面路径产品工作台 / 需求文档系统
对下游影响本步骤产出的《产品方案》与《交互方案》将作为第二阶段开发与UI并行启动的输入；UI据此绘图，开发据此排期；运营在下一步据此验收交互。

负责人与参与方

  • 负责人：产品

操作步骤

1. 将版本范围清单中的每个需求项拆解为可执行的产品方案（功能边界、关键流程、字段定义）。

2. 为每个需求项产出对应的交互方案（页面跳转、关键交互、状态流转）。

3. 整理为《产品方案》与《交互方案》两份文档，标注版本号与发布日期。

4. 完成后通知运营进入下一步验收。

关键产出物

  • 《产品方案》：功能边界、关键流程、字段定义。
  • 《交互方案》：页面跳转、关键交互、状态流转。

注意事项与坑点

  • 交互方案必须画出状态流转：不只是页面跳转，还要标注每个状态的进入/退出条件。
  • 不要在产品方案里直接定 UI 细节：UI 细节由步骤 4 的 UI 负责，产品方案只描述"做什么"不描述"怎么画"。
  • 完成后必须通知运营：不通知就卡住下一步，运营不知道要验收。

业务逻辑

产品独立完成：分解需求是产品的职责，不依赖其他角色。产出物的完整度直接决定步骤 3 运营验收能否发现方向性问题，也决定步骤 4 开发与UI能否并行启动。产出物不达标，会在步骤 3 被运营打回。

运营验收交互

③当前环节：③ 运营验收交互
页面路径交互评审会 / 线上评审
对下游影响本步骤是开发动手前的方向性关卡，验收通过后开发与UI才能进入步骤 4 启动；验收不通过则回到步骤 2 由产品调整方案，避免开发到一半才发现方向错误。

负责人与参与方

  • 负责人：运营

操作步骤

1. 运营收到产品通知后，组织交互评审（线上或线下）。

2. 对照《交互方案》逐项验收：交互是否符合业务场景、状态流转是否完整、关键路径是否顺畅。

3. 验收通过 → 进入步骤 4。

4. 验收不通过 → 回到步骤 2，产品根据运营反馈调整方案，重新提交运营验收。

关键产出物

  • 验收结论：通过 / 不通过。
  • 不通过时的反馈清单：逐条列出需调整的点。

注意事项与坑点

  • 验收必须在开发动手前完成：本步骤的核心价值就是前置拦截方向性错误，开发后再验收就失去意义。
  • 不通过必须给出可操作反馈：不能只说"不对"，必须逐条说明哪里不对、期望怎样。
  • 不通过只能回到步骤 2：不能跳过产品直接让开发改，否则产品方案与最终发布物不一致。

业务逻辑

运营单向关卡：运营只在本步骤出现，作为方向性验收的关卡。通过则退出流程直到步骤 4 内的UI回流验收再次出现；不通过则触发回流到步骤 2。本步骤的存在使得方向性返工成本被压到最低（开发尚未启动）。

启动开发与绘图

④当前环节：④ 启动开发与绘图
页面路径开发环境 / 设计交付工具
对下游影响本步骤开发与UI并行启动；UI产出物需回流给产品/运营验收后才能交付开发使用，避免UI方向错误导致开发返工；开发完成后进入步骤 5 写测试用例与自测。

负责人与参与方

  • 负责人（开发侧）：开发人员
  • 负责人（UI侧）：UI
  • UI回流验收：产品 / 运营

操作步骤

1. 开发人员根据《产品方案》《交互方案》进入开发，搭建页面骨架与业务逻辑。

2. UI 同步进入绘图，按交互方案产出设计稿。

3. UI 产出后回流给产品/运营验收：

  • 验收通过 → 交付开发使用，开发按设计稿调整UI细节。
  • 验收不通过 → UI 返工重绘，再次回流验收。

4. 开发完成初步功能后，进入步骤 5。

关键产出物

  • 设计稿：UI 产出，经产品/运营回流验收通过。
  • 可运行的开发版本：开发人员产出，覆盖《产品方案》全部功能点。

注意事项与坑点

  • UI 产出物未经回流验收不得直接交付开发使用：否则UI方向错误会传导到开发，造成更大返工。
  • 开发与UI必须并行：不能等UI全部画完再开发，会拖慢节奏；但UI的回流验收是必要关卡。
  • 回流验收不通过只能UI返工：不能让开发按错误方向继续，必须等UI修正后再交付。

业务逻辑

双线并行 + 单点验收：开发与UI并行启动以提速，但UI产出物必须经过产品/运营回流验收才能交付开发使用，这是本步骤内的方向性关卡。本步骤的设计使得UI错误被限制在UI侧，不会扩散到开发侧。

写测试用例并自测

⑤当前环节：⑤ 写测试用例并自测
页面路径开发环境 / 测试用例文档
对下游影响本步骤产出的测试用例将作为步骤 7 利珠组织测试的输入；开发自测通过后才能进入步骤 6 发版通知，避免发版后才发现基础bug。

负责人与参与方

  • 负责人：开发人员

操作步骤

1. 开发人员根据《产品方案》《交互方案》编写测试用例（覆盖功能点、边界、异常）。

2. 开发人员按测试用例逐条自测。

3. 自测通过 → 进入步骤 6。

4. 自测不通过 → 修复后重新自测，循环直到通过。

关键产出物

  • 测试用例文档：覆盖功能点、边界、异常，可交付测试人员直接使用。

注意事项与坑点

  • 测试用例必须覆盖异常路径：只测happy path无法发现真实问题，必须覆盖异常输入、空状态、并发场景。
  • 开发自测必须按测试用例执行：不能凭感觉测，必须按用例逐条勾选，确保覆盖。
  • 测试用例产出后必须可移交：步骤 7 利珠拿到测试用例要能直接组织测试，不能需要开发额外解释。

业务逻辑

开发人员独立完成：写测试用例与自测都是开发人员的职责。测试用例的完整度直接决定步骤 7 利珠测试的覆盖度；自测不通过则不能发版通知，避免给测试人员增加无效返工。

发版通知

⑥当前环节：⑥ 发版通知
页面路径群通知 / 邮件 / 项目协同工具
对下游影响本步骤在提交版本前 6 小时发出通知，给测试与相关方留出准备窗口；通知发出后利珠据此安排人员测试。

负责人与参与方

  • 负责人：产品

操作步骤

1. 产品在提交版本前 6 小时发出发版通知。

2. 通知内容包含：版本范围、发布时间、关联需求清单、测试用例位置、负责人联系方式。

3. 通知渠道：项目群 + 邮件（至少两个渠道，避免遗漏）。

4. 利珠收到通知后安排人员进入步骤 7 测试。

关键产出物

  • 发版通知：含版本范围、发布时间、关联需求、测试用例位置。

注意事项与坑点

  • 必须提前 6 小时：不足 6 小时会导致测试人员来不及准备，影响发布质量。
  • 通知内容必须与步骤 1 确认的版本范围逐字一致：不能在通知时擅自增减需求项，否则与最初确认口径不一致。
  • 必须多渠道通知：单一渠道容易遗漏，至少项目群+邮件。

业务逻辑

产品单向关卡：产品在本步骤作为发版通知的发布方，通知内容必须与步骤 1 双方确认的版本范围逐字一致。6 小时窗口是给测试人员的最低准备时间，不足则不允许提交。

安排人员测试

⑦当前环节：⑦ 安排人员测试
页面路径测试管理工具 / 测试执行环境
对下游影响本步骤由利珠拿到测试用例后组织人员测试；测试结果决定是否进入步骤 8 返工循环，或直接进入步骤 9 产品终验。

负责人与参与方

  • 负责人：利珠
  • 测试执行人：由利珠安排（不固定为某个角色）

操作步骤

1. 利珠收到产品发版通知后，根据测试用例范围安排测试人员。

2. 测试人员按测试用例逐条执行，记录通过/不通过。

3. 测试结果汇总给利珠。

4. 全部通过 → 进入步骤 9 产品终验。

5. 存在不通过项 → 进入步骤 8 返工修改。

关键产出物

  • 测试报告：每条用例的执行结果（通过/不通过 + 不通过原因）。

注意事项与坑点

  • 测试人员由利珠安排：测试人员不固定为某个角色，由利珠根据范围与人力调度决定。
  • 必须按测试用例执行：不能凭经验测，必须按开发产出的测试用例逐条勾选。
  • 不通过项必须记录原因：不能只说"不通过"，必须说明哪条用例、什么现象、期望结果。

业务逻辑

利珠单向关卡：利珠只在本阶段出现，作为测试组织的负责人。测试人员由利珠调度，不固定为某个角色，但责任由利珠承担。测试结果不通过则触发步骤 8 返工循环。

返工修改与循环测试

⑧当前环节：⑧ 返工修改与循环测试
页面路径开发环境 / 测试管理工具
对下游影响本步骤由开发人员根据测试报告修复问题，修复后回到步骤 7 由利珠安排复测，循环直到全部通过才进入步骤 9。

负责人与参与方

  • 负责人（修复侧）：开发人员
  • 负责人（复测侧）：利珠

操作步骤

1. 开发人员拿到测试报告后逐条修复问题。

2. 修复完成后通知利珠安排复测。

3. 利珠组织人员复测（按原测试用例 + 修复涉及范围）。

4. 复测通过 → 进入步骤 9。

5. 复测仍不通过 → 回到本步骤继续修复，循环直到通过。

关键产出物

  • 修复记录：每条不通过项的修复方式与修复人。
  • 复测报告：复测结果（通过/不通过 + 不通过原因）。

注意事项与坑点

  • 修复不能引入新问题：每次修复必须验证不破坏其他用例，不能只修当前bug。
  • 复测不能省略：修复后必须回到步骤 7 由利珠组织复测，不能由开发自测代替。
  • 循环无上限但要及时升级：若同一问题循环超过 3 次仍未解决，应升级到产品/东武评估是否需要从版本范围中剔除。

业务逻辑

双负责人循环：修复由开发人员负责，复测由利珠负责，两者形成闭环。循环直到全部测试用例通过才允许进入步骤 9，确保发布质量不依赖个人保证。同一问题循环超 3 次需升级，避免无限返工。

产品最终验收

⑨当前环节：⑨ 产品最终验收
页面路径体验环境 / 产品验收会
对下游影响本步骤是发布前的最后一道关卡，产品从产品视角（非测试视角）确认发布物符合产品预期；通过后才进入步骤 10 上线。

负责人与参与方

  • 负责人：产品

操作步骤

1. 产品在体验环境对发布物进行最终验收。

2. 验收维度：是否符合《产品方案》、是否符合《交互方案》、是否覆盖版本范围全部需求项。

3. 验收通过 → 进入步骤 10 上线。

4. 验收不通过 → 回到步骤 8 由开发人员修复，重新走步骤 7 → 步骤 8 → 步骤 9。

关键产出物

  • 终验结论：通过 / 不通过 + 不通过清单。

注意事项与坑点

  • 产品视角验收，非测试视角：本步骤不重复测试人员的功能测试，而是从产品预期视角确认整体符合度。
  • 不通过必须回到步骤 8：不能跳过测试流程直接让开发改，必须经过利珠组织的复测。
  • 终验是关卡非形式：产品必须真实体验发布物，不能只看测试报告就放行。

业务逻辑

产品单向关卡：产品在本步骤作为发布前的最终决策方。终验通过则授权上线，不通过则触发回到步骤 8 的修复循环。本步骤使得发布权最终落在产品手里，避免测试通过但产品预期不符的发布物被发布。

上线并通知

⑩当前环节：⑩ 上线并通知
页面路径生产环境 / 通知渠道
对下游影响本步骤完成版本正式上线，并通知所有人（含"其他"角色）发布完成；通知后整个版本发布流程闭环。

负责人与参与方

  • 负责人（上线操作）：开发人员
  • 负责人（通知发出）：产品

操作步骤

1. 开发人员执行上线操作（部署到生产环境）。

2. 上线完成后产品验证关键路径可用。

3. 产品发出上线通知：含版本范围、上线时间、变更说明、负责人联系方式。

4. 通知渠道：项目群 + 邮件 + 全员通知（覆盖"其他"角色）。

5. 通知发出后整个流程闭环。

关键产出物

  • 上线记录：上线时间、操作人、上线版本号。
  • 全员通知：含版本范围、变更说明、负责人。

注意事项与坑点

  • 上线后必须产品验证关键路径：不能上线完就通知，必须先验证核心功能可用。
  • 通知必须覆盖"其他"角色：不能只通知核心团队，要让所有相关方都知道发布了什么。
  • 通知内容必须包含变更说明：不能只说"已上线"，必须说明本次变更了什么，方便其他角色评估影响。

业务逻辑

双负责人收尾：上线操作由开发人员执行，通知由产品发出。本步骤是整个流程的闭环点，发布后通知全员确保信息透明，使整个发布流程的产出对所有人可见——这也是本指引的核心目标"让需求透明化，所有人都知道发布了什么"的最终落点。

需求背景与目标

1.1 为什么要做

我们承接两类业务，都需要依托商家作为小程序主体和商户号主体，由言成完成部署和后续运营配置：

  • 支付代收小程序（A）：用户在小程序下单付款，资金直接进入商家商户号收款；商品上架和发货由言成完成。
  • 返现小程序（B）：用户在我们这里领券下单后，获得返现金额，返现通过商家商户号转账到用户的微信零钱。

两个小程序的业务模型不同，但部署流程相同：商家负责前三步主体准备（注册小程序、准备商户号、授权及入驻），后两步由我们执行（部署小程序、配置物料和商品库）。本指引把整条流程合并写一遍，覆盖双方需要执行的全部动作。

1.3 最终目标

  • 主体资质就位：商家完成两个小程序注册（工具-比价类目）+ 一个商户号开通双能力 + 授权及入驻，形成可被部署的基础环境。
  • 小程序部署上线：言成完成两个小程序的部署绑定与物料/商品库配置，业务可正常承接营业。

2.2 阶段划分与阅读说明

后续正文按照业务实际发生顺序线性展开，不按操作端分别集中介绍。根据当前部署闭环，可划分为：

1. 第一阶段：商家主体准备（主要参与方：商家）：商家完成两个小程序注册（工具-比价类目）、一个商户号开通双能力（JSAPI 支付 + 商家转账到零钱）、两个小程序授权及入驻三步，形成可被部署的基础环境。

注册小程序

①当前环节：① 注册小程序
页面路径微信公众平台 > 注册 > 小程序
对下游影响注册后获得的 AppID、原始 ID（gh_ 开头）、小程序密钥（AppSecret）将作为第二阶段部署绑定的核心字段；选择的"工具-比价"服务类目决定后续该小程序可承接的业务范围。

主体类型选择

  • 企业/个体工商户：推荐使用企业主体注册；个体工商户也可，但部分支付能力受限。
  • 所需材料：营业执照、法人身份证、对公账户（个体户可用法人个人银行卡）、300 元认证费（或法人微信扫码认证免费）。
  • 主体名称：使用商家营业执照上的全称，不要缩写。
  • 两个小程序各注册一个账号：A（支付代收）和 B（返现）需要分别注册独立的小程序账号，不能共用。

注册入口与操作步骤

1. 访问 https://mp.weixin.qq.com/，点击「立即注册」→ 选择「小程序」。

2. 填写邮箱（未绑定过微信公众号/小程序的邮箱）、密码，完成邮箱激活。

3. 主体类型选择：企业 / 个体工商户。

4. 填写主体信息：上传营业执照、填写法人信息、对公账户信息。

5. 法人微信扫码完成主体验证（推荐）或打款验证（300 元，到账后自动退回）。

6. 完成注册，进入小程序后台。A 和 B 两个账号分别完成一次。

服务类目选择（重要）

  • 类目路径：小程序后台 > 设置 > 基本设置 > 服务类目 > 添加类目。
  • 一级类目：工具。
  • 二级类目：比价。
  • 类目资质：工具-比价类目一般无需额外资质，可直接选择通过；如系统提示需补充资质，按提示上传。
  • 不可选错：选错类目可能导致后续支付能力无法开通或被风控。A 和 B 两个小程序均使用同一类目。
  • 不要选"电商平台"类目：电商平台类目需要 ICP 证、第三方平台资质等，门槛高且不适合本业务模型。

关键字段获取

  • AppID：小程序后台 > 开发 > 开发管理 > 开发设置；用途：第二阶段绑定部署的核心标识，每个小程序各有一个。
  • AppSecret：小程序后台 > 开发 > 开发管理 > 开发设置 > 重置后复制；用途：与 AppID 配对用于接口调用；重置后旧密钥立即失效，需同步给言成。
  • 原始 ID（gh_ 开头）：小程序后台 > 设置 > 基本设置；用途：部分跳转场景使用。

注意事项与坑点

  • 邮箱不可复用：注册用的邮箱不可绑定过其他微信公众号/小程序；推荐申请新邮箱。
  • 类目不要选"电商平台"：电商平台类目需要 ICP 证、第三方平台资质等，门槛高且不适合本业务模型。本指引统一选"工具-比价"。
  • AppSecret 重置同步：重置 AppSecret 后旧密钥立即失效；重置后必须第一时间同步给言成，否则线上小程序立即报错。
  • 类目修改次数有限：每月类目修改次数有限，确认后再添加。
  • 小程序名称：建议命名为"XX 比价""XX 优惠"等与工具-比价类目相符的名称，避免名称被驳回。
  • 服务器域名白名单：本阶段暂不配置，由言成在第二阶段完成。
  • 两个小程序分别注册：A 和 B 是两个独立小程序账号，不要试图用一个 AppID 承载两种业务。

业务逻辑

两个小程序均使用相同注册流程：A（支付代收）和 B（返现）的注册步骤、类目、主体资质完全一致，差异在第二阶段的部署配置和商户号能力使用方式。建议商家一次性注册两个小程序账号，避免后续来回切换主体。

准备商户号

②当前环节：② 准备商户号
页面路径微信支付商户平台 > 入驻
对下游影响商户号是支付能力和转账能力的载体，A 小程序需要使用该商户号完成 JSAPI 支付收款，B 小程序需要使用该商户号完成"商家转账到零钱"向用户返现。

一个商户号开通两种能力

商家只需开通一个微信支付商户号，在该商户号下同时开通：

  • JSAPI 支付（小程序支付）：A 小程序用户下单付款，资金直接进入商家商户号收款。
  • 商家转账到零钱：B 小程序用户领券下单后，由该商户号发起向用户微信零钱的转账，完成返现。

开通操作步骤

1. 进入微信支付商户平台 https://pay.weixin.qq.com/，点击「商家入驻」或「立即接入」。

2. 使用与小程序同主体的营业执照入驻，确保商户号主体与小程序主体一致。

3. 提交营业执照、法人身份证、对公账户、超级管理员信息等。

4. 等待审核（通常 1-3 个工作日），审核通过后获得商户号（MCHID）。

5. 在商户号下关联两个小程序：进入商户平台 > 产品中心 > AppID 账号管理，分别关联 A 小程序和 B 小程序的 AppID。

6. 开通两种产品能力：

  • 进入商户平台 > 产品中心，开通「JSAPI 支付」（默认开通）。
  • 进入商户平台 > 产品中心，申请开通「商家转账到零钱」（需满足条件，审核后开通）。

商家转账到零钱的开通条件

  • 商户号状态正常，无重大违规记录。
  • 商户号需在 90 天内有真实交易流水（建议先开通 JSAPI 支付并产生少量测试交易）。
  • 部分商户号主体类型受限，建议提前在商户平台查询资格。
  • 若无法立即开通，先完成 A 小程序的部署和测试交易，待满足条件后再补开 B 的转账到零钱能力。

关键字段获取

  • 商户号 MCHID：商户平台 > 账户中心 > 商户信息；用途：部署支付能力时的核心字段。
  • 商户 API 密钥：商户平台 > 账户中心 > API 安全 > 设置 API 密钥；用途：用于签名，与 MCHID 配对；设置后无法在商户平台直接查看，必须保存好。
  • 商户证书：商户平台 > 账户中心 > API 安全 > 申请 API 证书；用途：用于转账到零钱等敏感接口调用，下载得到 apiclient_cert.p12 文件。
  • 证书序列号：商户平台 > 账户中心 > API 安全 > 查看证书；用途：与证书文件配对使用。
  • AppID 关联关系：商户平台 > 产品中心 > AppID 账号管理；用途：确认 A、B 两个小程序均已关联到本商户号。

注意事项与坑点

  • 主体必须一致：商户号主体必须与小程序主体一致，否则无法关联 AppID。
  • API 密钥保管：API 密钥设置后无法在商户平台直接查看，请保存好；丢失只能重置，重置后线上立即报错。
  • 转账到零钱需先有流水：新开商户号不能立即开通转账到零钱，需 90 天内有交易。若 B 小程序部署期紧，可与商家提前规划流水产生节奏。
  • 商户证书下载：证书文件 apiclient_cert.p12 必须妥善保存，言成在第二阶段需要使用；丢失只能重新申请。
  • 商户号建议单独开通：建议为本指引的两个小程序单独开通商户号，避免资金混用和对账复杂。
  • 若商家已有商户号：可复用现有商户号，但需在 AppID 账号管理中关联本指引的两个新小程序 AppID，并确认两种能力均已开通。

业务逻辑

商户号能力差异：A 小程序使用 JSAPI 支付（收款方向：用户→商家商户号），B 小程序使用商家转账到零钱（付款方向：商家商户号→用户）。一个商户号同时承载这两种能力，商家只需维护一个商户号即可覆盖两个小程序的资金流。两种能力的开通时机不必同步——A 可立即开通并产生流水，B 待条件满足后再开通。

授权及入驻

③当前环节：③ 授权及入驻
页面路径系统后台 > 商户入驻
对下游影响入驻后，商家的两个小程序 AppID 将与代码系统建立绑定关系，作为第二阶段言成部署和配置物料/商品库的承载平台。

入驻操作步骤

1. 言成向商家提供系统入驻入口（链接或二维码）。

2. 商家使用小程序主体绑定的微信扫码进入入驻流程。

3. 系统自动读取商家小程序的主体信息（企业名称、营业执照号、法人等）。

4. 商家确认入驻协议，提交两个小程序的 AppID（A 小程序 AppID、B 小程序 AppID）。

5. 系统校验 AppID 与主体一致性，校验通过后完成入驻。

6. 入驻成功后，商家在系统后台拥有一个商户主账号。

关键字段

  • 商户主体名称：来源为系统自动读取；用途：入驻后商户账号的显示名称。
  • A 小程序 AppID：来源为商家填写；用途：第二阶段绑定 A 小程序的标识。
  • B 小程序 AppID：来源为商家填写；用途：第二阶段绑定 B 小程序的标识。
  • 商户管理员微信：来源为商家填写；用途：后续言成与商家在系统内的协作账号。

注意事项与坑点

  • 两个 AppID 都要填：入驻时务必同时填写 A、B 两个小程序的 AppID，遗漏任一将导致言成在第二阶段无法绑定该小程序。
  • AppID 主体必须与入驻主体一致：如商家填入其他主体的 AppID，校验会失败。
  • 入驻后不要切换主体：入驻后若小程序主体变更，会导致入驻关系失效，需要重新入驻。
  • 小程序主体注销则入驻失效：若商家后续注销小程序，代码系统中的入驻关系也会自动失效。
  • 入驻前先完成 ①②：建议商家完成 ① 注册、② 商户号开通后再入驻，避免入驻后还要回头补主体资质。

业务逻辑

入驻是双方交接点：本步骤是商家主体准备的最后一步，也是言成接手部署的起点。入驻完成后，商家的前期准备工作结束，后续部署和配置均由言成在系统后台完成，商家只需配合提供必要字段（如 AppSecret、商户 API 密钥、商户证书等敏感信息）。

部署小程序

④当前环节：④ 部署小程序
页面路径系统后台 > 商户管理 > 小程序部署
对下游影响部署完成后，A 小程序可承接用户付款（资金进入商家商户号），B 小程序可承接用户领券下单并触发返现流程。

部署前必须收到的商家资料清单

  • A 小程序 AppID + AppSecret
  • B 小程序 AppID + AppSecret
  • 商户号 MCHID
  • 商户 API 密钥
  • 商户证书文件 apiclient_cert.p12
  • 商户 API 证书序列号

任一缺失即无法完成部署，先与商家确认补齐。所有敏感字段通过加密渠道传递，不要走明文聊天工具。

部署操作步骤

1. 登录系统后台，进入对应商户账号。

2. 进入「小程序部署」页面，分别选择 A 小程序和 B 小程序。

3. 填写以下字段并保存：

  • AppID（自动带出商家入驻时填写的 AppID，可校对）
  • AppSecret（向商家获取，填入后保存）
  • 服务器域名白名单（request 域名、uploadFile 域名、downloadFile 域名等，按系统文档配置）

4. 进入「支付配置」页面，填写商户号相关字段：

  • 商户号 MCHID
  • 商户 API 密钥
  • 上传商户证书文件 apiclient_cert.p12
  • 填写证书序列号

5. 分别配置两个小程序的支付能力：

  • A 小程序：启用 JSAPI 支付，资金收款到商家商户号。
  • B 小程序：启用商家转账到零钱，配置返现触发规则。

6. 提交部署，系统自动校验 AppID + AppSecret + 商户号关联关系。

7. 校验通过后，部署完成，小程序可正常访问。

关键字段配置说明

  • AppSecret：配置位置为小程序部署页；必须与商家小程序后台设置的 AppSecret 一致；若商家后续重置 AppSecret，本字段需同步更新，否则线上立即报错。
  • 服务器域名白名单：配置位置为小程序部署页；必须包含系统业务域名，否则小程序内业务接口调用失败；每月修改次数有限，建议一次性配置完整。
  • 商户 API 密钥：配置位置为支付配置页；必须与商户平台设置的 API 密钥一致。
  • 商户证书：配置位置为支付配置页；用于 B 小程序的转账到零钱接口调用；证书默认 1 年有效，到期前需在商户平台续期并重新上传。

部署后的自检

  • 用真机扫码进入 A 小程序，尝试下单支付一笔小额测试订单（如 1 分钱或 1 元），确认资金进入商家商户号。
  • 用真机扫码进入 B 小程序，触发一次返现流程，确认商家商户号成功向测试用户微信零钱转账。
  • 检查系统后台日志，确认接口调用无异常。
  • 自检全部通过后，通知商家部署完成，进入 4.2 配置物料和商品库。

注意事项与坑点

  • AppSecret 同步：商家若在小程序后台重置 AppSecret，必须第一时间告知言成，否则线上立即报错。
  • 服务器域名每月修改次数有限：建议一次性配置完整，避免反复修改。
  • 商户证书有效期：商户证书默认 1 年有效，到期前需在商户平台续期并重新上传；建议建立证书到期台账。
  • 两个小程序的支付配置独立：A 和 B 在系统内是两条独立的部署记录，不要混淆字段，AppID/AppSecret/商户号不要张冠李戴。
  • 测试金额要小：自检时使用 1 分钱或 1 元订单，避免大额资金误转。
  • 敏感字段加密传递：AppSecret、商户 API 密钥、证书文件不要走明文聊天工具传递，建议使用加密渠道。

业务逻辑

部署完成即可营业（技术层面）：本步骤完成后，两个小程序从技术层面已具备承接业务的能力，但物料和商品库尚未配置，用户进入小程序仍看不到可购买/可领取的内容，需要继续完成 4.2 的物料和商品库配置。A 和 B 的部署记录相互独立，但共用一个商户号——商户号字段只配置一次，但要在 A、B 两个部署记录中分别引用。

配置物料和商品库

⑤当前环节：⑤ 配置物料和商品库
页面路径系统后台 > 商品/物料管理
对下游影响配置完成后，A 小程序展示可下单商品，B 小程序展示可领取的优惠券和返现规则，两个小程序进入可营业状态。

配置内容范围

本步骤统一为两个小程序配置业务内容：

  • A 小程序（支付代收）：商品库——上架商品、配置价格、库存、发货模板。
  • B 小程序（返现）：物料库——配置优惠券（领券规则、面额、有效期），配置返现规则（返现金额、触发条件、上限）。

配置操作步骤

1. 登录系统后台，进入对应商户账号。

2. 进入「商品库管理」（A 小程序用），新建商品：

  • 填写商品名称、商品图片、商品详情、价格、库存。
  • 关联发货模板（言成这边发货，使用言成的发货主体）。
  • 设置商品上架状态为「上架」。

3. 进入「物料/优惠券管理」（B 小程序用），新建优惠券和返现规则：

  • 优惠券：填写券名称、面额、领取条件（如满 X 元可用）、有效期、发放总量。
  • 返现规则：配置返现金额、触发条件（如领券后下单成功）、返现上限、返现到账方式（即时 / 延迟）。

4. 配置完成后，在 A、B 小程序内分别验证：

  • A 小程序：商品列表是否展示，下单支付流程是否走通，资金是否进入商家商户号，发货是否由言成完成。
  • B 小程序：优惠券是否可领取，用户领券下单后是否触发返现，返现是否到账用户零钱。

5. 确认无误后，正式上线运营。

关键配置字段说明

  • 商品名称/图片/价格/库存：所属为 A 商品库；用途为决定 A 小程序商品列表展示和下单流程。
  • 发货模板：所属为 A 商品库；用途为关联言成这边的发货主体，下单后由言成这边发货；务必关联言成发货主体，不要使用商家的发货模板。
  • 优惠券面额/有效期/总量：所属为 B 物料库；用途为决定 B 小程序可领取的券。
  • 返现金额/触发条件/上限：所属为 B 物料库；用途为决定用户领券下单后获得的返现。

注意事项与坑点

  • 发货主体是言成这边：A 小程序的商品虽然由商家收款，但发货由言成这边完成，发货模板必须关联言成的发货主体，不要使用商家的发货模板。
  • 返现金额要事先核算：返现金额来自商家商户号转账到用户零钱，转账金额和手续费需提前与商家对账确认，避免商家商户号资金不足导致返现失败。
  • 优惠券发放总量有限制：超发会导致用户领取后无法使用，建议设上限并监控。
  • 商品上架后不可频繁改价：频繁改价可能触发微信侧的风控，建议改价前下架再重新上架。
  • B 小程序的返现触发条件与领券绑定：返现必须基于"领券下单"才触发，避免无券直接下单也返现造成资金损失。
  • 测试时使用小额订单：A 测试用 1 分钱或 1 元订单；B 测试用小额返现，避免返现金额超过测试预算。
  • 正式上线前与商家对账：返现资金来自商家商户号，上线前需与商家确认商户号余额充足，避免上线后返现失败影响用户体验。

业务逻辑

配置完成进入营业：本步骤是整个部署流程的最后一步。配置完成后，两个小程序均具备承接业务的能力——A 小程序有可下单付款的商品（资金进入商家商户号，由言成这边发货），B 小程序有可领取的优惠券和返现规则（用户领券下单后由商家商户号转账返现到用户零钱）。两个小程序正式进入可营业状态，本指引流程闭环完成。

业务概览

页面路径系统后台 > 方笑天小程序
对下游影响方笑天的新小程序可承接电商下单与餐餐补配置两套业务，进入可营业状态。

业务范围

方笑天的新小程序承接 2 套业务：

  • 电商：上架、配置、发货、售后 — 全流程由言成运营执行，只作用于方笑天的新小程序。
  • 餐餐补：配置链接路径，数据页只显示方笑天的数据 — 由言成运营执行。

实操人员

  • 统一由言成运营执行：上架、配置、发货、售后均由言成运营在系统后台完成，方笑天仅作为小程序主体提供方。

技术方案路线

两套业务采用不同的隔离策略：

  • 电商 → 字段隔离：在订单表、商品分类表、发货售后表上加字段做归属过滤，同一张数据表支持多方可见。
  • 餐餐补 → 物理复制菜单：复制一套菜单，加后缀 _方笑天，新菜单只配置方笑天的，旧菜单保留言成的。

业务逻辑

两套业务双轨并行：电商用字段隔离策略保留共用数据 + 多方可见能力，餐餐补用物理复制菜单策略实现数据强隔离。两套业务边界清晰，互不干扰。策略选择依据业务本身的数据载体——电商以商品/订单为载体，字段过滤即可隔离；餐餐补以菜单为载体，菜单本身就是天然的隔离边界，物理复制更直接、风险更低。

电商方案：字段隔离

★当前环节：电商接入
页面路径系统后台 > 商品/订单管理
对下游影响通过字段过滤让方笑天的新小程序能承接上架、配置、发货、售后，同一商品库可被多方运营人员按归属方过滤查看。

字段改动清单

共改动 3 处表结构：

  • 订单表加字段：订单来源
    • 字段类型：前端返
    • 取值：标识订单来自哪个小程序（如方笑天小程序、言成小程序）
    • 用途：按订单来源过滤、统计各小程序订单
  • 商品分类表加字段：归属方
    • 字段类型：单选枚举
    • 取值：全部 / 言成 / 方笑天
    • 默认值：全部
    • 用途：决定分类下商品对各运营方的可见性
  • 发货 · 售后表加字段：来源小程序
    • 字段类型：标识字段
    • 取值：标识发货/售后归属哪个小程序
    • 用途：按小程序维度做发货和售后归属过滤

商品与分类的挂载关系（多选）

  • 一个商品可同时挂载到多个分类下，挂载关系为多选。
  • 当商品挂多个分类时，其可见归属方 = 所挂载分类归属方的并集。

跨分类并集示例

text
A 分类（零食）归属：方笑天
B 分类（酒水）归属：言成
        ↓
商品"可乐"同时挂 A + B 两个分类
        ↓
可乐的可见归属方 = A 归属 ∪ B 归属 = {方笑天, 言成}
        ↓
结果：方笑天和言成的运营人员均能看到可乐

关键字段配置说明

  • 订单来源：由前端在用户下单时返回，标识订单来自哪个小程序；后端按此字段做订单过滤和统计。
  • 归属方：配置位置为商品分类管理页；决定该分类下商品对各运营方的可见范围；默认"全部"以兼容存量数据。
  • 来源小程序：配置位置为发货/售后表；与订单来源对应，标识发货/售后归属哪个小程序。

注意事项与坑点

  • 归属方默认全部：新增分类默认归属"全部"，避免存量商品突然不可见；新建言成或方笑天专属分类时需手动改为对应归属方。
  • 可乐类跨分类商品：跨分类商品按并集归属方处理，不要试图用单一归属方覆盖，否则会导致一方运营人员看不到本应可见的商品。
  • 订单来源必须前端返：前端下单时必须把订单来源字段传给后端，遗漏会导致订单无法按小程序过滤，统计和发货归属都会出错。
  • 发货/售后归属与订单来源对应：发货/售后的"来源小程序"必须与订单来源保持一致，避免出现方笑天订单被言成发货的串单问题。
  • 挂载关系为多选：商品挂载分类时允许多选，但要确认归属方并集后的可见范围符合预期，避免误挂导致商品对不该可见的一方暴露。

业务逻辑

字段隔离保留共用商品库：电商方案不在表层面复制数据，而是通过字段过滤实现"同一商品库、多方可见"。订单来源决定订单归属，归属方决定商品可见范围，来源小程序决定发货/售后归属。三方字段协同形成完整的电商业务隔离闭环，避免数据冗余和对账复杂。

餐餐补方案：复制菜单

★当前环节：餐餐补接入
页面路径系统后台 > 餐餐补菜单
对下游影响通过复制菜单物理隔离方笑天与言成的餐餐补配置和数据，新菜单只配置方笑天的，旧菜单保留言成的。

字段改动清单

无字段改动 — 通过菜单复制 + 后缀命名实现隔离。

菜单复制规则

  • 旧菜单（无后缀）：原菜单路径保留，归属言成；数据页只显示言成的数据。
  • 新菜单（加后缀 _方笑天）：复制旧菜单得到，归属方笑天；数据页只显示方笑天的数据。

配置操作步骤

1. 复制旧餐餐补菜单，新菜单路径 = 旧菜单路径 + _方笑天。

2. 在新菜单中配置方笑天的餐餐补链接路径。

3. 旧菜单保持言成的配置不变。

4. 验证新菜单数据页只显示方笑天的数据，旧菜单数据页只显示言成的数据。

关键字段配置说明

  • 菜单后缀：统一使用 _方笑天；新菜单路径 = 旧菜单路径 + _方笑天。
  • 数据隔离：新菜单的数据页只展示方笑天的数据，旧菜单的数据页只展示言成的数据；两套菜单物理隔离，互不影响。

注意事项与坑点

  • 后缀统一用 _方笑天：所有方笑天的菜单统一使用 _方笑天 后缀，避免出现 _fxt、_方笑天2026 等不一致命名导致菜单混乱。
  • 新菜单是复制不是新建：复制旧菜单得到新菜单，确保菜单结构与字段一致；不要手动新建菜单导致结构差异，否则后续维护成本高。
  • 数据页不要混数据：新菜单数据页必须只显示方笑天的数据；如出现言成数据，需排查菜单复制时是否带过来旧数据，并清理。
  • 旧菜单配置不要动：复制后旧菜单保留言成配置不变，避免影响言成现有业务；如确需调整言成配置，在旧菜单独立操作。

业务逻辑

物理复制实现强隔离：餐餐补方案不用字段过滤，而是通过复制菜单 + 后缀命名做物理隔离。两套菜单独立配置、独立数据页，不存在数据交叉风险。策略选择原因：餐餐补的链接路径配置和数据展示以菜单为载体，菜单本身就是天然的隔离边界，比加字段更直接、风险更低、维护成本更可控。

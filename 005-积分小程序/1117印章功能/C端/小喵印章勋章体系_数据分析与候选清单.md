## 六、结论分三档

### 强烈建议做（数据充分、覆盖率健康、故事性强）
- **time**：午餐、晚餐、夜宵——合计覆盖近半用户，时段信号最干净
- **taste**：碳水、炸鸡、奶茶、甜品——品类关键词命中率高，辨识度强
- **habit**：双平台、凑单、专情一家——行为定义明确，且未被营销化

### 可做（信号真实但需控制门槛）
- 探店、咖啡、火锅、水果、轻食：覆盖率 2%–7%，适合做稀有/彩蛋层
- 周末：47% 覆盖但过于宽泛，建议只作为其他勋章的叠加条件，不单独设一枚

### 不建议做（数据无法支撑，请勿上线）
- **onsite 到店/自提**：无到店/自提字段，数据无法判断，需要补充履约方式字段
- **city 全家族（新城市/返乡/城市探索）**：无 `city` 字段，商家名中的地名不可靠，需要补充城市字段
- **season 节气/立秋/冬至**：仅 29 天数据，无法覆盖节气，需要补充跨年订单数据
- **usage 收藏/分享/邀请/红包满减**：无对应行为字段，需要补充行为埋点
- **usage 晒单**：`pic_url` 是平台商品图非用户晒单，需要补充用户上传图片记录
- **usage 填头像昵称**：无头像字段，需要补充用户资料字段
- **event 免单/中奖/活动**：无活动标识，需要补充活动参与记录

## 七、建议调整/下线的现有勋章及理由

> 未提供现有 34 枚勋章的具体清单，此处只能按 8 大家族方向给调整建议，无法逐枚比对。

1. **city 家族整体暂缓**：本数据无法验证任何一枚，建议全部转为"待接入城市字段后启用"，不要靠商家名硬猜城市。
2. **season 家族整体下线或隐藏**：29 天数据不足以支撑节气类解锁判断，强行上线会导致大量用户永远无法解锁。
3. **usage 家族的分享/邀请/晒单/收藏**：建议下线或改为纯展示位——勋章是情感工具，缺数据的勋章会变成空壳。
4. **onsite 家族**：若产品实际无到店业务，建议直接砍掉；若需保留，先补履约方式字段。
5. **taste 家族过宽的勋章**（如有"美食家"类泛品类勋章）：建议拆成上述 8 个具体品类，覆盖率从"几乎人人有"降到有区分度的 5%–32%。
6. **habit 家族的"常客"类**：若现门槛按总单数设计，建议改为"同一家店复购"（2.99% 覆盖），更符合"只认一家"的情感叙事，且避免与高频刷单用户绑定。

### 8.5 代码判断逻辑

核心就是**关键词命中**，但要注意三点：细分优先的顺序、同一订单取图幂等、词表配置化不要硬编码。

```js
// 1. 规则表：顺序即优先级，细分在前、宽泛在后
const CATEGORY_RULES = [
  { key: 'milk_tea', words: ['奶茶','茶饮','益禾堂','蜜雪','茉莉奶白','古茗','茶百道','霸王茶姬','伯牙绝弦','奶绿','果茶','柠檬茶','杨枝甘露','生椰','芋泥'] },
  { key: 'coffee',   words: ['咖啡','美式','拿铁','瑞幸','星巴克','库迪','卡布奇诺'] },
  { key: 'dessert',  words: ['蛋糕','甜品','面包','蛋挞','泡芙','酸奶','冰淇淋','糖水','布丁','蛋黄酥','桃胶','水果捞'] },
  { key: 'hotpot',   words: ['火锅','麻辣烫','冒菜','串串','关东煮','砂锅','鸡公煲','干锅','烤鱼'] },
  { key: 'fried',    words: ['炸鸡','鸡排','鸡腿','鸡柳','鸡堡','汉堡','薯条','炸串','烧烤','烤鸭','鸡翅','叉烧'] },
  { key: 'staple',   words: ['米饭','盖饭','拌饭','炒饭','牛肉饭','米线','面条','拉面','小笼包','包子','水饺','饺子','馄饨','米粉','河粉','螺蛳粉','凉皮','肉夹馍','烧饼','饭','面','粉'] },
  { key: 'salad',    words: ['沙拉','轻食','减脂','健康餐','素食','蔬菜'] },
  { key: 'fruit',    words: ['水果','果切','草莓','蓝莓','苹果','香蕉','西瓜','葡萄','榴莲'] },
  { key: 'drink',    words: ['汤','粥','豆浆','可乐','矿泉水','冰红茶','饮料','卤','豆干','小吃'] },
];

// 2. 命中函数：命中即返回，未命中返回 'general'
function matchCategory(title = '') {
  for (const rule of CATEGORY_RULES) {
    if (rule.words.some(w => title.includes(w))) return rule.key;
  }
  return 'general';
}

// 3. 稳定哈希：保证同一订单每次取到同一张图（幂等），不同订单分散
function hash(str) {
  let h = 0;
  for (let i = 0; i < str.length; i++) h = (h * 31 + str.charCodeAt(i)) >>> 0;
  return h;
}

// 4. 取图主逻辑
function pickImage(order, imagePool) {
  if (order.pic_url) return { url: order.pic_url, source: 'real' };  // ① 真实商品图
  const cat = matchCategory(order.goods_title);                       // ② 品类命中
  const pool = imagePool[cat] || imagePool.general;                   // ③ 通用兜底
  const seed = `${order.user_id}-${order.id || order.platform_order_id}`;
  return { url: pool[hash(seed) % pool.length], source: cat };
}
```

实现要点：
- **匹配用 `includes` 不用正则**：中文关键词子串匹配足够，性能更好；词表要支持正则别名时再上正则。
- **顺序敏感**：`milk_tea`、`coffee` 等细分桶必须在 `staple` 的宽泛词（`饭`/`面`/`粉`）之前，否则会被抢先归类。
- **取图幂等**：用 `user_id + 订单ID` 做哈希取模，而不是 `Math.random()`，保证刷新页面图不跳变。
- **词表配置化**：`CATEGORY_RULES` 和 `imagePool` 放配置表/数据库，别写死在代码里，方便运营持续养词（当前未命中仍有 37%，需要定期补充）。
- **兜底必须保留**：任何词表都覆盖不全，`imagePool.general` 至少备 8 张，否则会出现空白图。

### 8.6 待确认事项

1. **打卡图定位**：是"代表这单吃了啥"（品类图够用），还是要"用户真实晒单照"？后者图库解决不了，需补充上传字段——当前数据无法判断。

> 版本：v0.1

> 当前阶段：仅完成规划，不修改或生成交互稿代码  
> 参考框架：`../奶茶争霸赛二期/奶茶争霸赛二期_交互稿.html`

## 1. 规划结论

本次不把“奶茶争霸赛二期”当作普通页面复刻，而是复用它的**交互稿审阅工作台框架**：

- 左栏按“流程 / 页面”两种方式浏览。
- 中栏展示流程步骤、页面帧与抽屉状态。
- 中央使用 392 × 820 手机模拟器承载真实交互。
- 右栏同步展示当前帧的入口条件、字段逻辑、交互说明与待确认项。
- 所有页面、流程、状态和说明由配置表驱动。

印章交互稿将保留这套审阅能力，但全部业务内容重写为：

1. 全局底部 Tab：印章、积分、积分商城、我的。
2. 印章内部子页面：记录日历、印章墙。
3. 本月记录弹层、当日记录弹层、月度相册、订单记录详情、印章详情。
4. 饿了么订单自动取图入历。
5. 美团订单匹配后台配置图/默认图入历。
6. 记录更新、统计联动和印章自动解锁。

原始“奶茶争霸赛二期”目录保持只读，不直接修改。

## 2. 现有交互稿框架拆解

### 2.1 文件与运行方式

```text
奶茶争霸赛二期/
├─ 奶茶争霸赛二期_交互稿.html       约 5.38 MB / 3060 行
├─ 奶茶争霸赛二期_交互稿.html.bak
└─ assets/
   ├─ avatar1.jpg ... avatar4.jpg/png
   └─ milktea1.webp ... milktea3.jpg
```

- 纯原生 HTML、CSS、JavaScript。
- 无 `package.json`、构建工具、前端框架和后端依赖。
- 直接双击 HTML 或通过静态服务器即可运行。
- 仅 Google Fonts 依赖网络；业务数据全部是前端 Mock。
- 不使用 `fetch`、XHR、WebSocket、LocalStorage，刷新后状态重置。

### 2.2 审阅工作台骨架

现有 `.app` 使用三列 Grid：

| 区域 | 宽度/结构 | 作用 |
|---|---|---|
| 左栏 `.rail` | 236px | 流程/页面模式切换与目录 |
| 中栏 `.flowcol` | 306px | 流程步骤、页面帧、抽屉分组 |
| 主舞台 `.stage` | 剩余宽度 | 手机模拟器 + 右侧说明面板 |
| 手机 `.phone` | 392px × 最大 820px | 模拟移动端产品界面 |
| 说明 `.changelog` | 280px | 当前帧的条件与逻辑说明 |

手机模拟器内已经预留：

- `#screen`：页面内容。
- `#tabbar`：全局底栏；当前稿被 CSS 隐藏，新稿重新启用。
- `#sheet`：Bottom Sheet、居中弹窗与遮罩。
- `#toast`：轻提示。

### 2.3 四张核心配置表

| 配置 | 原稿作用 | 印章稿用途 |
|---|---|---|
| `ROUTES` | 注册所有页面帧 | 注册日历、印章墙、相册、详情及占位页 |
| `FLOWS` | 组织逐步业务流程 | 组织订单回流、月度回顾、印章解锁与退款流程 |
| `PAGE_TREE` | 按页面查看所有帧/抽屉 | 按功能域查看页面状态与弹层 |
| `CHANGELOG` | 当前帧入口条件、逻辑和改动 | 改名展示为“交互说明”，保留数据结构 |

配置表与 View 代码分离，因此同一页面可以同时出现在多个流程中，无需复制页面实现。

### 2.4 渲染与状态机制

现有框架采用：

```text
配置表
→ 全局运行时状态
→ xxxView() 返回页面模板字符串
→ frameView() 分发页面
→ currentSheetView() 分发弹层
→ renderAll() 同步渲染页面、抽屉、目录、流程和说明
```

交互使用统一事件委托：

- `data-act`：业务动作。
- `data-go`：切换帧或打开抽屉。
- `data-step`：定位流程步骤。
- `data-autosheet`：进入步骤时自动打开弹层。
- `data-mode`：流程/页面模式。
- `data-flow`、`data-page`：左栏导航。

核心可复用方法为：`go()`、`openSheet()`、`closeSheet()`、`renderAll()`、`goFlowStep()` 和 Toast。

### 2.5 可直接复用的交互能力

- 流程步骤跳转与当前步骤高亮。
- 页面帧选择器。
- Bottom Sheet 上滑与遮罩淡入。
- 居中弹窗缩放淡入。
- Toast 轻提示。
- 成功态、空态、禁用态和失败态。
- 弹层与宿主页关联。
- 遮罩、关闭按钮及 `Esc` 关闭。
- 页面旁同步展示业务逻辑说明。

### 2.6 现有框架问题与处理

| 现状 | 印章稿处理 |
|---|---|
| HTML 约 5.38 MB | 大图全部放 `prototype/assets`，不内嵌 Base64 |
| 状态为多个全局变量 | 收敛为一个 `state` 对象 |
| 直接点击中间步骤可能受之前状态污染 | 用 `applyStepState()` 为每步恢复确定场景 |
| `.tabbar` 被强制隐藏 | 重新启用并实现四项全局 Tab |
| 无窄屏响应式 | 仍定位为桌面评审台；保证常用桌面尺寸可用 |
| Google Fonts 依赖网络 | 保留字体栈，同时提供完整系统字体回退 |
| 右栏名为“改动记录” | 展示文案改为“交互说明” |
| 单个点击处理器较长 | 按导航、日历、记录、印章、模拟订单分段 |

## 3. 本次交互稿目标与边界

### 3.1 必须实现

- 四项全局底部 Tab 可点击：印章、积分、积分商城、我的。
- 所有截图能力都在“印章”Tab 内。
- 印章内部使用顶部二级导航切换“记录日历 / 印章墙”。
- 不出现手工新增记录的 `+` 按钮。
- 日历、本月弹层、月度相册与详情使用同一份 Mock 记录数据。
- 饿了么记录使用订单回传图。
- 美团记录使用后台匹配配置图；未命中时使用平台/系统默认图。
- 新订单进入后，日历角标、杯数、店铺数、列表和相册同步更新。
- 达到条件时只触发一次印章解锁反馈。
- 页面模式与流程模式均能独立浏览。

### 3.2 本次不实现

- 真实饿了么、美团接口或鉴权。
- 真实订单同步、图片下载和对象存储。
- 积分发放/扣减规则、积分明细流水、积分商城交易和“我的”业务。
- 生产级路由、持久化、权限和埋点上报。
- 真实后台管理系统；只在交互说明和 Mock 规则中演示匹配结果。

### 3.3 原型模拟原则

原型演示的是“业务结果与交互反馈”，不伪装成真实接口：

- 外部下单继续使用虚线流程节点或说明帧。
- “平台回调”“图片匹配”“规则计算”由固定场景模拟。
- 右侧交互说明明确展示模拟输入、判断条件与结果。
- 任何统计均由 Mock 数据计算，避免页面间手填数字不一致。

## 6. 页面帧规划

### 6.1 页面（路由）与帧

**菜单口径**：弹窗不算页面，挂在宿主页下；整页跳转但不是 Tab 入口的，进二级页面；App 外的页面进外部页面。

| 层级 | 页面 | 状态帧（Route Key） | 弹层 |
|---|---|---|---|
| 一级 | A 印章-日历 | `stamp-calendar` 有记录 / `stamp-calendar-newbie` 无单用户 / `stamp-calendar-empty` 空月份 / `stamp-calendar-syncing` 订单同步中 / `stamp-calendar-fallback` 美团配置图 / `stamp-calendar-error` 月份请求失败 | `month-records` 本月记录、`day-records` 当日记录、`newbie-guide` 新用户引导弹窗 |
| 一级 | B 印章-印章墙 | `badge-wall-all` 标签图鉴 / `badge-wall-newbie` 无单用户图鉴 / `badge-wall-unlocked` 我的收藏 / `badge-wall-empty` 空态 / `badge-computing` 判定计算中 | `badge-filter` 筛选、`badge-detail-unlocked` 标签详情（已收）、`badge-detail-locked` 标签详情（未点亮）、`badge-unlock` 标签收入反馈 |
| 一级 | C 积分 | `points-home` 积分首页（签到条静态展示） | — |
| 一级 | D 积分商城 | `mall-placeholder` 范围占位 | — |
| 一级 | E 我的 | `mine-placeholder` 范围占位 | — |
| 二级 | F 月度相册 | `month-gallery` 按月回顾 | `month-picker` 月份选择 |
| 二级 | G 订单记录详情 | `record-detail-eleme` 饿了么订单 / `record-detail-meituan` 美团配置图 / `record-image-failed` 图片解析失败 | `order-invalidated` 退款失效 |
| 外部 | H 外部 | `external-eleme` 饿了么订单 / `external-meituan` 美团订单 / `image-rule-demo` 后台图片规则命中 | — |

合计 21 个状态帧 + 9 个弹层。

- **一级页面**＝底部 Tab 入口；印章 Tab 下的「日历」与「印章墙」是平级一级页，通过页内切换走。
- **二级页面**＝整页跳转、无 Tab 入口：月度相册（从日历「月度回顾」进）、订单记录详情（从记录卡片进）。
- **外部页面**＝非 App 内页面，只演示订单回流与后台图片规则，不参与 App 导航。

相同 View 的不同状态通过场景参数驱动，避免复制整份 HTML。`ROUTES` 与 `PAGE_TREE` 由同一份 `PAGE_DEFS` 生成，帧不可能被塞进别的页面，弹层也不能跨页挂。

### 6.2 抽屉与弹层

| Sheet Key | 形式 | 宿主页 | 作用 |
|---|---|---|---|
| `month-records` | 大圆角 Bottom Sheet | A 印章-日历 | 本月记录，复刻截图 3 |
| `day-records` | Bottom Sheet | A 印章-日历 | 同日多条记录列表 |
| `month-picker` | Bottom Sheet | F 月度相册 | 切换年月 |
| `badge-filter` | Bottom Sheet | B 印章-印章墙 | 标签族 / 我的收藏筛选 |
| `badge-detail-locked` | Bottom Sheet 或详情层 | B 印章-印章墙 | 未点亮标签：同类规模 + 故事 + 档位链 |
| `badge-detail-unlocked` | Bottom Sheet 或详情层 | B 印章-印章墙 | 已收标签：档位链 + 收入日期 |
| `badge-unlock` | 居中弹窗 | B 印章-印章墙 | 档位进阶后的单次反馈 |

| `newbie-guide` | 居中弹窗 | A 印章-日历 | 无单用户首次进站的玩法引导（主流程 A） |

### 6.3 `PAGE_TREE` 分组

- **一级页面（5 页）**

  - C 积分：1 帧（签到条静态展示）
  - D 积分商城：1 帧（占位）
  - E 我的：1 帧（占位）
- **二级页面（2 页）**
  - F 月度相册：1 帧 + 1 弹层
  - G 订单记录详情：3 帧 + 1 弹层
- **外部页面（1 组）**
  - H 外部：3 帧

## 7. 流程规划

### Flow 01：日历与本月回顾

```text
印章 Tab
→ 记录日历
→ 点击“本月”
→ 打开本月记录弹层
→ 收藏一条记录
→ 打开订单记录详情
```

验证：月份统计、卡片数量、图片、时间和收藏状态一致。

### Flow 02：月度相册

```text
记录日历
→ 点击右侧相册入口
→ 月度相册
→ 打开月份选择
→ 切换历史月份
→ 打开记录详情
```

验证：年月切换、空月、关闭返回和滚动位置。

### Flow 03：印章浏览

```text
记录日历
→ 内部切换印章墙
→ 筛选已解锁/未解锁
→ 打开印章详情
→ 查看条件、进度或解锁日期
```

验证：未解锁与已解锁状态不依赖素材外观猜测。

### Flow 04：饿了么订单自动入历并解锁

```text
下单前：本月 4 杯
→ 外部饿了么订单达到有效状态
→ 获取券抵扣商品图片
→ 自动生成第 5 条日历记录
→ 月历、本月统计、弹层、相册同步为 5
→ 满足“本月 5 杯”
→ 弹出印章解锁反馈
→ 印章墙出现解锁日期
```

验证：使用 `ELEME_ORDER` 图片来源，重复执行不增加第 6 条。

### Flow 05：美团订单使用后台配置图

```text
外部美团订单达到有效状态
→ 平台无订单图片
→ 按券/活动/SKU/商品/店铺规则匹配
→ 命中后台配置图
→ 自动生成日历记录
→ 详情显示图片来源和命中规则
```

分支：未命中业务规则时使用美团平台默认图，再无则使用系统默认图。

### Flow 06：订单退款/记录失效

```text
已有 ACTIVE 日历记录
→ 模拟订单退款
→ 记录转为 INVALID
→ 从日历、月度弹层与相册隐藏
→ 杯数、店铺数和未完成印章进度重算
→ 展示普通印章保留/严格策略撤销说明
```

验证：退款事件重复执行仍保持同一状态。

### 16.1.1 页面结构整理（按「一页一路由」重排）

原先每个状态各占一条路由，新增的异常态又被单独归到「系统状态」页，导致同一个页面的状态散落两处。现改为单一数据源：

## 18. 主次流程重排与无单用户设计（2026-11-16 新增）

### 18.1 流程结构：先分主次，再排功能

原流程按功能罗列（浏览/入历/异常/积分），没有主次。本次改为两层结构：

| 层级 | 分组 | 流程 | 回答的问题 |
|---|---|---|---|
| 主流程 A | 新用户（无单） | `A1` 新用户首单闭环 | 一单没有的用户进来，页面怎么显示、动线怎么跑 |
| 主流程 B | 老用户（有单） | `01` 日历与本月回顾、`04` 饿了么订单入历并解锁 | 有单用户进来，怎么回顾、怎么继续攒章 |
| 次要流程 | 查询与回顾 | `02` 月度相册、`03` 印章浏览 | 功能入口怎么查 |
| 次要流程 | 异常与边界 | `05` 美团配置图、`06` 退款失效、`07` 三页异常帧 | 出问题怎么兜底 |
| 次要流程 | 积分模块 | `08` 积分页概览 | 相邻模块的边界 |

主流程 A 的 5 步：进站引导弹窗 → 愿望清单 → 锁章转化 → 去下单 → 首单回流（解锁「第一杯」）。

### 18.2 无单用户的设计原则：空态不是空白，是预告

| 位置 | 原表现 | 现表现 |
|---|---|---|
| 日历空态（`stamp-calendar-newbie`） | 「暂无记录」+ 全 0 统计 | 预告卡「你的第一枚印章，还差 1 单」+ CTA「去许愿」+ 社会证明条 |
| 印章墙（`badge-wall-newbie`） | 空态文案 | 5 枚锁章灰阶全展示 = 愿望清单，进度 0 / N + 「已有 X 人解锁」 |
| 锁章详情（`badge-detail-locked`） | 条件 + 进度 | 增加社会证明行 + 「差 N 笔即可解锁，达成后自动发放」+ 双平台 CTA |
| 首次进站 | 无 | `newbie-guide` 居中弹窗：下单 → 自动记账 → 集印章 → 解锁勋章，CTA 跳印章墙 |

关键判断：

1. **锁章详情就是转化落地页**——新用户不需要被教育"去下单"，他需要看到"差多少、点哪去"。
2. **引导弹窗不做独立机制**——它是「首页配置改造」弹窗体系里的一种运营可配置弹窗，触发条件多一个「无单用户」维度，同样遵守「同一时刻只弹 1 个」。
3. **社会证明分两级**——锁章卡/详情放精准数字（已有 X 人解锁），墙顶放氛围数字（本月 X 位用户集齐）。
4. **数字口径属于后端**——原型为 mock；新章上线数字小时用「新章首发」标签兜底，不展示虚假数字。

### 18.3 菜单挂载（不变原则）

- `stamp-calendar-newbie` → 一级页面 A 印章-日历（第 2 帧）
- `badge-wall-newbie` → 一级页面 B 印章-印章墙（第 2 帧）
- `newbie-guide` → 挂宿主一级页 A（弹窗不进页面层级）
- 合计 21 帧 + 9 弹层，`PAGE_DEFS` 单一数据源，断言卡全部通过

### 18.4 待业务决策

1. 社会证明的统计口径：累计解锁人数 / 周期解锁人数 / 同城人数，需后端确认。
2. 引导弹窗触发频次：仅首次，还是「7 天未下单」再唤回一次。
3. 新用户引导弹窗与运营弹窗的优先级：若同刻都有触发，谁先弹。
4. 「差 N 笔」是否含跨平台订单（当前按全平台有效订单计）。

## 19. 勋章页升级为「标签图鉴」（2026-11-16 晚）

### 19.1 为什么改

«18» 把无单用户做成了「差 N 笔去下单」的转化动线，业务反馈已实测跑不通：营销型太强，用户没有"我要成为某类人"的感觉。本次把整页从**集章册**改成**身份图鉴**——印章不再是奖励，是一条条可对照自己的标签。

公式：**数据（同类规模）× 场景（共鸣）＝ 标签（身份）**
例：2.3 万用户 × 早上都来一杯咖啡 → 「早八续命打工人」。

### 19.2 结构变化

| 维度 | 改前 | 改后 |
|---|---|---|
| 单元 | 一枚章一个固定条件 | 一个标签族 + 多档位（同店 3 / 5 / 15 单） |
| 组织 | 平铺网格 + 已解锁/未解锁筛选 | 7 个族分组 + 族筛选（入场与日常 / 时间节律 / 口味偏好 / 行为指纹 / 城市与迁徙 / 节气时令 / 活动彩蛋） |
| 视觉 | 圆章图片素材 | 刻字印章（族色 + 单字印面），无素材依赖 |
| 三态 | 已解锁 / 未解锁 | 已收（走完档位）/ 进阶中（达首档未走完）/ 未点亮 |
| 文案 | 解锁条件、差 N 笔 | 同类规模 + 一句人群故事；只报下一档**名字**，不报数字条件 |
| CTA | 去饿了么下单 / 去美团下单 | 主按钮「我也是这类人」（兴趣向，点了记入图鉴 +1）；下单降为底部灰字「顺手去点一杯 ›」 |

### 19.3 数据与规则

- `TAG_FAMILIES`：7 族，各带色值与一句族说明。
- `TAG_LIBRARY`：**32 枚**首发标签，每枚含 `family / seal(印面字) / holders(同类规模) / story(一句话) / tiers(档位链) / stage(老用户 mock 进度) / signal(来源) / stageNew(新用户 mock 进度) / art(可选，章面插画路径)`。
- `signal`：`order` 订单派生（默认）｜`signup` 注册资料｜`checkin` 签到｜`coupon` 领券｜`link` 转链｜`invite` 邀请。**除 order 外都不需要下单**。
- `computedBadges()` 三态计算：`locked / progress / unlocked`；newbie 与 empty 场景强制归零。
- 老用户（5 单同店、双平台、1 城）默认：已收 7 枚（第一次就上头 / 老板记得你的甜度 / 全平台端水大师 / 一杯安顿新城市 / 初次见面喵 / 露脸的小喵 / 连签一周），进阶中 2 枚，其余未点亮。
- 无单用户默认：已收 2 枚（初次见面喵、露脸的小喵，来自 `stageNew`），其余 30 枚归零。**§22 起定为 2 枚**（领券达人退出新人闭环，仅在积分页领满 6 张时独立反馈）。
- 标签判定依赖的信号全部可算：时间、日期/节气、品类、门店、平台、频次、活动；**不依赖天气与情绪**（见《全平台标签图鉴-场景库.md》）。

### 19.4 页面挂载（不变原则）

### 23.3 去白底（本次唯一的坑）

素材是白底方图。最初想用 `mix-blend-mode:multiply` 让白底融进米色纸面，实测**失败**：
JPEG 的白不是纯 255，且边缘有压缩噪点，乘上去会在抽屉里留一个清晰的浅灰方块。

改成真去底：`assets/badges/trim-badge-bg.py`
1. 四个角分别 `floodfill` 到透明（`thresh=48`）。从角起始只会吃掉连通的背景白，猫脸、缎带米色在描边内部，不会被误伤。
2. 只对 alpha 通道做 0.8px 高斯模糊，给硬边补抗锯齿，不动 RGB。
3. `getbbox()` 裁掉空白边，缩到 480px 存 PNG。
4. 结果：480×474 / 480×478，不透明像素 73.9%，视觉上完全融进任意浅色底。

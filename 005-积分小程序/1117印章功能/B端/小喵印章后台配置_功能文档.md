# 小喵印章后台配置

> 本文档为 **B 端运营配置端** 功能文档，只补齐「小喵印章」勋章体系背后的运营配置能力。C 端日历与勋章图鉴的交互实现由《产品需求文档.md》《印章_交互稿.html》承载，本文档不重复描述。所有触发条件口径、关键词桶划分与取图优先级，一律以《小喵印章勋章体系_数据分析与候选清单.md》为准。

## 1. 需求背景与目标

### 1.1 为什么要做

「小喵印章」的 C 端形态已经定稿：用户每完成一笔外卖订单，日历自动生成一条打卡记录并配一张图，行为累计达标后解锁对应勋章。但勋章的名称、印面字、图、文案，以及打卡图"该配哪一张"的匹配规则，目前全部写在前端与脚本里——运营改一个字都要发版。更关键的是美团订单拿不到商品图，必须有可运营的品类图片桶与兜底图把每一单接住，否则会出现大量无图的打卡记录。

- **配置范围：**
- [[4.1|勋章家族]]：维护图鉴的分区名、排序与是否展示
- [[4.2|勋章配置]]：维护勋章的展示元素（名称、印面字、勋章图、解锁前文案、解锁条件）与启停
- [[4.3|图片规则配置]]：维护「商品名关键词 → 图片池」的匹配桶与唯一的兜底桶，决定每条打卡记录命中哪一张图

另有 **[[4.4|勋章设计]]**：只读文档页，一张表列清 17 枚勋章的家族、触发条件、预估覆盖率与设计意图，**不承载任何配置**。

**不做的部分（已确认结论）：** 解锁判定不做成可配置项。触发条件类型、判定参数与门槛值一律由研发按勋章写死在代码里，后台只做只读回显——避免运营改口径导致勋章错发或永不触发。

```text
改造前

勋章与取图规则写死在前端，调整需要发版
美团订单无商品图，打卡记录无图可展示

改造后

运营在配置端维护家族、勋章展示元素，以及关键词图片桶和兜底桶
        ↓
订单完成后系统生成日历记录，按「真实商品图 → 品类桶 → 兜底桶」取图
        ↓
系统按研发写死的口径判定 → 用户解锁勋章 → 图鉴按配置展示
```

### 1.2 一句话业务模型

```text
积分订单数据（goods_title、platform、created_at、shop_name）
        +
运营维护的家族、勋章展示元素与关键词图片桶
        +
必填且不可删除的兜底图片池
        ↓
日历记录生成并按优先级取图 → 系统按写死口径判定 → 勋章解锁 → 图鉴展示
```

### 1.3 最终目标

- **展示可运营：** 家族分区、勋章名称/印面字/图/两段用户可见文案全部由运营维护，改名换图改文案不依赖发版。
- **判定收口在研发：** 解锁口径不在后台暴露，杜绝运营配错门槛导致勋章乱发或永不触发。
- **打卡图不空缺：** 任何一笔订单都能取到一张图，美团无商品图的订单由关键词桶与兜底桶接住。

### 1.4 页面原型与图片说明

C 端日历与勋章图鉴效果由外部原型《印章_交互稿.html》承载；本文档只产出 B 端配置端交互原型，不重复 C 端展示。

## 4. 第一阶段：勋章与取图配置

### 4.1 勋章家族 — 列表页（新增页面）

#### 业务背景

当前环节：① 维护家族与勋章配置<br>
页面路径：运营配置后台 > 小喵印章 > 勋章家族<br>
对下游影响：家族决定 C 端图鉴的分区名与先后顺序；隐藏的家族在 C 端不展示，其下勋章随之一并不展示<br>
表格类型：列表页<br>

#### 字段说明

家族是勋章的第一层归类，只承担展示职责，不参与解锁判定。C 端图鉴按本页排序依次分区，分区内展示该家族下状态=启用的勋章。

本期预置 8 个家族，与 C 端交互稿的 8 族一一对应。其中「节气时令」「使用纪念」「特别时刻」在当前订单字段下没有任何可验证的勋章，**默认隐藏**——避免 C 端出现三个空分区。「初见日常」因新增两枚事件型勋章（注册即得、完善资料）改为展示。

家族只保留最小字段集（ID、名称、排序、是否展示），不统计勋章数、不记录更新时间：家族是纯展示分类，知道它叫什么、排在第几、要不要显示就够了。

##### [列表页字段]

| 字段名称 | 字段类型 | 列表 | 详情 | 新增 | 字段解释 |
| --- | --- | --- | --- | --- | --- |
| 家族ID | string | 是 | 是 | 是（创建后不可修改） | **数据来源：** 运营人员填写。<br>**逻辑：** 小写英文（如 `time`、`taste`），全局唯一，与 C 端交互稿的 family 字段保持同值。<br>**用途：** 程序识别的唯一键，创建后不可改。 |
| 家族名称 | string | 是 | 是 | 是（可编辑） | **数据来源：** 运营人员填写。<br>**逻辑：** 2–6 个字（如"口味偏好"），全局不可重名。<br>**用途：** C 端图鉴的分区标题。 |
| 排序 | number | 是 | 是 | 是（可编辑） | **数据来源：** 运营人员填写。<br>**逻辑：** 正整数，数值越小越靠前，决定图鉴分区的上下顺序。<br>**用途：** 控制分区展示次序。 |
| 是否展示 | enum（展示、隐藏） | 是 | 是 | 是（可编辑） | **数据来源：** 运营人员选择。<br>**逻辑：** 隐藏后 C 端不渲染该分区，其下勋章一并不展示；新增家族默认隐藏。<br>**用途：** 控制分区是否出现在图鉴里。 |

##### 弹窗字段分组

| 组名 | 字段 |
| --- | --- |
| 基本信息 | 家族ID、家族名称、排序、是否展示 |

#### 列表交互

**交互：新增家族**  <br>
**业务用途**：新增一个图鉴分区，填 ID、名称与排序后保存；是否展示默认关闭，等该家族下有勋章后再打开，避免出现空分区。<br>

**交互：编辑家族**  <br>
**业务用途**：调整名称、排序与是否展示；保存后 C 端图鉴按新顺序重新分区渲染。家族ID 不可修改。<br>

**交互：删除家族**  <br>
**业务用途**：删除该家族，二次确认后生效；**该家族下仍有勋章时禁止删除**（由系统校验），需先把勋章改到其他家族。已下线家族的历史解锁记录保留在库中。<br>

#### 业务逻辑

**ID 不可改：** 家族ID 与 C 端交互稿的 family 字段同值，改了会导致历史勋章找不回分区，因此创建后锁定。

**空分区默认隐藏：** 新增家族默认不展示，配好勋章后再手动打开，防止图鉴出现空白分区。

**删除有前置条件：** 有勋章归属的家族不可删除，必须先迁移勋章；只允许改名、调序或隐藏。

**排序冲突：** 排序数值重复时，按更新时间先后排列，保存时提示冲突但不阻断。

### 4.2 勋章配置 — 列表页（新增页面）

#### 业务背景

当前环节：① 维护家族与勋章配置<br>
页面路径：运营配置后台 > 小喵印章 > 勋章配置<br>
对下游影响：勋章保存并启用后，C 端图鉴按下发的展示元素渲染；解锁由研发写死的口径判定，后台的改动只影响展示，不改变判定结果<br>
表格类型：列表页<br>

#### 字段说明

勋章分两层信息：一层是用户看得见的展示元素（名称、印面字、图、**解锁前文案**、**解锁条件**），一层是系统判定的解锁口径（触发条件类型、参数、门槛值、档位与档位名）。

两段文案的展示时机是分开的：**未解锁只出「解锁前文案」**（模糊暗示，不给门槛），**解锁后才出「解锁条件」**（直白说明做了什么）。这样运营配文案时只需要回答两个问题：还没拿到时说什么、拿到之后说什么。

**第二层全部由研发按勋章写死在代码里，后台只读回显，不提供任何编辑入口。** 运营能看到这枚勋章"怎么算出来的"，但改不了——这是为了避免口径被误改导致勋章错发或永不触发。

**本页不支持新增勋章。** 代码里没有判定逻辑的勋章永远不会解锁，只会变成一个空壳，所以新勋章必须走研发发版。后台只做两件事：编辑预置的 17 枚、启停。

本期预置 17 枚：15 枚来自《小喵印章勋章体系_数据分析与候选清单.md》第五章候选（订单数据可验证），另 2 枚为事件型勋章（初次见面喵、露脸的小喵），不依赖订单数据。逐枚判定口径见 4.4。

#### 列表交互

**交互：编辑勋章**  <br>
**业务用途**：调整名称、印面字、图、家族、两段用户可见文案与启停；保存后 C 端按下发内容重新渲染。解锁口径（含档位阈值与档位名）只读，改判定口径或档位需要研发发版。<br>

**交互：删除勋章**  <br>
**业务用途**：删除该勋章配置，二次确认后生效；C 端不再展示，但用户已解锁的历史记录保留在库中不删除。**已上线过的勋章建议改用停用而非删除**，删除后代码里的判定逻辑会失去配置对象。<br>

**交互：本页无「新增勋章」入口**  <br>
**业务用途**：页面头部不提供新增按钮。新增勋章必须由研发在代码里补上判定逻辑并发版，否则这枚勋章永远不会解锁。<br>

#### 业务逻辑

**判定口径不下放：** 触发条件类型、判定参数、门槛值，以及档位数量与档位名，全部由研发写死。后台仅在弹窗中以只读形式回显一条「解锁口径」描述，任何情况下不提供编辑控件。此约束为已确认结论。

**名称唯一：** 勋章名称全局不可重名，重名时保存失败并提示。

**两段文案的边界：** 「解锁前文案」不得出现数字与具体触发条件，只做模糊暗示；「解锁条件（用户可见）」可含数字，但只在解锁后展示。解锁口径本身属内部信息，不直接下发 C 端，对外只通过这两段文案表达。

**解锁条件须与解锁口径一致：** 解锁条件是判定口径的用户可读版本。运营改文案不会改判定——文案与实际口径不一致会让用户看到"说一套判一套"。因此保存时若两段文字差异过大，弹窗内提示运营核对上方只读的「解锁口径」；要改判定必须研发发版。

**印面字与勋章图是互斥兜底关系：** C 端渲染逻辑为 `勋章图非空 ? 显示图 : 显示印面字`。因此印面字必填、勋章图选填——34 枚勋章不可能同时出图，先有字也不会开天窗。

**只支持编辑与启停：** 预置 17 枚可编辑、可停用、可删除，但不支持新增。到店/自提、节气、收藏分享邀请晒单、免单中奖等方向因订单数据缺对应字段（`city`、`items`、行为埋点、活动标识等）暂不预置，字段补齐后由研发连同判定逻辑一起发版。

**停用不删档：** 停用后 C 端不再展示该勋章，也不再触发新解锁；用户已解锁的记录留在库中。

### 4.3 图片规则配置 — 列表页（新增页面）

#### 业务背景

当前环节：② 维护图片规则与兜底<br>
页面路径：运营配置后台 > 小喵印章 > 图片规则配置<br>
对下游影响：每条日历记录按本页桶的优先级匹配 `goods_title` 取图；未命中任何桶时落到兜底桶，兜底桶缺失会导致打卡记录无图<br>
表格类型：列表页<br>

#### 字段说明

取图分三层：`pic_url` 非空直接用真实商品图；否则用 `goods_title` 匹配品类桶；再未命中就落兜底桶。真实商品图只覆盖饿了么约 30% 的订单，美团订单 `pic_url` 为空——所以品类桶与兜底桶承担了大部分取图量，是整个配置的重点。

#### 列表交互

**交互：新增桶**  <br>
**业务用途**：新增一个品类桶，填桶标识、关键词与图片池后保存启用；保存后命中的订单立即按新桶取图。<br>

**交互：编辑桶**  <br>
**业务用途**：调整名称、优先级、关键词与图片池；保存后 C 端按新规则取图，已生成的记录在再次打开时会按新图片池重新取图。<br>

**交互：删除桶**  <br>
**业务用途**：删除该桶配置，二次确认后生效；兜底桶不提供删除入口。删除后其关键词覆盖的订单转由后续优先级桶或兜底桶承接。<br>

**交互：切换「真实商品图优先」全局开关**  <br>
**业务用途**：位于列表顶部，默认开启。开启时 `pic_url` 非空的订单一律用真实商品图，不进入关键词匹配；关闭时全部订单强制走关键词桶，用于真实商品图质量出问题时紧急兜底。<br>

#### 业务逻辑

**匹配顺序即优先级：** 按优先级数值升序逐个桶匹配 `goods_title`，命中第一个即停止，未命中任何桶时落兜底桶。优先级相同时按更新时间先后排序，并在保存时提示冲突。

**兜底桶唯一且强制：** 全局恰好 1 个桶的「是否兜底」=是，不可删除、不可停用，图片池不少于 8 张。缺少兜底桶时系统拒绝保存任何其他桶的删除操作——这是避免打卡记录出现空图的最低保障。

**真实商品图只覆盖饿了么：** 实测数据中 `pic_url` 仅饿了么约 30% 订单有值，美团订单 100% 为空，因此美团订单全部由关键词桶与兜底桶承接。

**图片数量锚点：** 按订单占比配置——兜底桶 8–10 张、米面碳水 6–8 张、炸鸡烧烤 4–5 张、奶茶/甜品/火锅/咖啡/汤饮各 3–4 张、水果/轻食各 2–3 张，合计 35–45 张。若改用猫咪主题插画统一风格，可整体取下限约 30 张。

**改图会追溯：** C 端按「用户 + 订单」哈希取模选图，只要图片池不变，同一订单每次都是同一张；一旦增删该桶的图片，历史记录再次打开时图会变。这是已确认可接受的行为，后台不做冻结。

**关键词持续维护：** 当前词表对订单的命中率约 62.6%，其余约 37.4% 落兜底桶。停用某个桶等于把该品类的全部订单推给兜底桶，视觉上会明显泛化，操作前需评估订单占比。

**与勋章判定解耦：** 本页关键词只服务配图。勋章判定用的关键词写死在代码里，两套词各自演进——运营在本页加词不会影响任何勋章的解锁条件。

### 5.1 日历记录生成与取图 — 移动端展示页（改造页面）

有效订单完成后，系统按下单时间在日历上生成一条打卡记录，并按「真实商品图 → 关键词桶 → 兜底桶」三层取图。同一订单重复生成时取图结果保持一致。记录生成后按研发写死的各勋章口径累计判定，达到门槛即解锁对应勋章及其档位。

### 6.1 查看日历与勋章图鉴 — 移动端展示页（改造页面）

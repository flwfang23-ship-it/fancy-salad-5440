# 美团及淘宝淘客业务处理方案

> 文档定位：产品需求文档（PRD）/ 研发需求评审
> 适用范围：产品、研发、测试团队
> 版本：v1.0 ｜ 日期：2026-11-11

## 一、美团业务处理方案

### 1. 美团联盟

**处理方案：**

沿用现有美团联盟推广位的配置及使用逻辑，复用现有推广位体系，无需额外开发两套推广位兼容方案。

**目标：**

- 统一推广位管理逻辑。
- 复用现有配置及业务能力。
- 降低重复开发成本，避免多套推广位逻辑带来的维护问题。

### 2. 美团高佣

**处理方案：**

美团高佣业务暂不接入积分体系，不参与积分返还及积分相关业务逻辑。

## 二、淘宝淘客转链业务方案

### 1. 订单状态定义

接入淘宝淘客订单数据，需支持以下订单状态：

| 订单状态 | 业务说明 |
| --- | --- |
| 已付款 | 用户已完成付款 |
| 已收货 | 用户已确认收货 |
| 已失效/关闭 | 订单失效或关闭 |
| 维权中 | 订单正在进行售后维权 |
| 维权完成 | 订单维权流程已结束 |

### 2. 前端开发需求

1. **新增淘客转链入口**：补充淘宝商品转链入口，支持用户通过平台入口完成商品转链及推广跳转。
2. **新增淘客订单入口**：增加淘客订单查询入口，支持用户查看通过平台产生的淘宝推广订单及相关信息。

### 3. 后端开发需求

#### （1）订单同步机制

- 新增淘宝淘客订单定时拉取任务。
- 定时获取淘宝淘客订单数据。
- 根据订单状态更新本地订单信息。
- 根据订单状态触发对应的积分处理逻辑。

#### （2）积分项配置

- 新增「淘客返积分」开关。
- 支持独立控制淘宝淘客业务是否参与积分返还。

#### （3）积分规则配置

新增以下积分配置参数：

- **佣金返积分比例**：根据订单佣金金额及配置比例计算用户应返积分。
- **兜底积分**：当正常计算所得积分低于兜底积分时，按兜底积分发放。
- **风控积分**：命中风控规则的用户，按照风控积分标准发放积分。

#### （4）推广位配置

- 新增淘宝淘客推广位配置能力。
- 支持推广位的独立配置及管理。

#### （5）积分流水配置

- 新增「淘宝积分流水」类型。
- 记录淘宝淘客订单产生的积分发放记录，便于后续查询、核对及追踪。

#### （6）订单管理

- 新增淘宝淘客订单数据管理能力。
- 记录订单信息、订单状态及关联用户信息，为后续积分发放和订单查询提供数据支持。

## 三、淘宝淘客积分业务规则

### 1. 积分到账规则

以淘宝淘客订单状态作为积分到账判断依据。

**正常积分到账节点：**

- 订单状态为「已付款」时，触发积分发放。
- 订单状态为「已收货」时，触发积分发放。

**不触发正常积分发放的订单状态：**

- 已失效/关闭
- 维权中
- 维权完成

### 2. 风控订单定义

以下订单状态定义为风控订单：

- 维权中
- 维权完成

风控订单不参与正常积分发放及兜底积分计算。

### 3. 用户风控规则

以用户维度统计风控订单数量。

**风控触发条件：**

当用户的风控订单数量超过 8 笔时，触发用户风控机制。

**风控处理规则：**

用户触发风控后，其后续所有符合积分发放条件的淘宝淘客订单，统一按照「风控积分」规则发放积分，不再按照正常佣金返积分规则计算。

### 4. 兜底积分规则

针对符合正常积分发放条件的订单（已付款、已收货），增加兜底积分机制。

**计算规则：**

- 根据订单佣金及佣金返积分比例，计算正常应返积分。
- 若计算所得积分低于配置的兜底积分，则按照兜底积分发放。
- 若计算所得积分高于或等于兜底积分，则按照正常计算结果发放。
- 风控订单不参与兜底积分计算。

## 四、核心业务规则汇总

| 业务场景 | 处理规则 |
| --- | --- |
| 美团联盟 | 复用现有推广位逻辑 |
| 美团高佣 | 不接入积分体系 |
| 淘客订单已付款 | 触发积分发放 |
| 淘客订单已收货 | 触发积分发放 |
| 淘客订单已失效/关闭 | 不发放积分 |
| 淘客订单维权中 | 计入风控订单，不发放正常积分 |
| 淘客订单维权完成 | 计入风控订单，不发放正常积分 |
| 用户风控订单数量不超过 8 笔 | 按正常积分规则计算 |
| 用户风控订单数量超过 8 笔 | 后续符合条件的订单统一按风控积分发放 |
| 正常计算积分低于兜底积分 | 按兜底积分发放 |
| 风控订单 | 不参与兜底积分计算 |

**方案核心：**

美团业务以复用现有能力为主，避免重复开发；淘宝淘客业务新增独立的转链、订单同步及积分管理能力，通过订单状态判断、用户风控机制及兜底积分机制，实现淘宝淘客积分发放的完整闭环。

## 五、建议研发评审时补充确认的细节

有几个地方建议在正式进入开发前明确，避免后续出现积分重复发放或风控规则理解不一致的问题：

1. **积分幂等性**：同一淘宝订单从已付款更新为已收货时，是否需要防止二次发放积分？建议同一订单只发放一次。
2. **风控统计口径**：超过 8 笔风控订单，是按历史累计统计，还是按某个时间周期统计？
3. **风控积分计算方式**：风控积分是固定值，还是仍然按照佣金比例计算？
4. **维权完成后的处理**：如果此前已付款并发放积分，后续进入维权流程，是否需要扣回已发放积分？
5. **订单状态回退**：如果订单状态发生变化，是否需要支持积分撤回或重新计算？

> **特别建议**：第 1 和第 4 点一定要在研发评审中确认，这会直接影响积分账务准确性和后续售后处理逻辑。
